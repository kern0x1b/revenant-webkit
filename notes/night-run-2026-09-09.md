# The night of 9 September

A log written as the work happened, so progress is visible without reading the
diff. Every number here was measured on the device; where something is not
measured, it says so.

## Rules this run held to

One run is not evidence. Memory is three cold runs of four heavy sites, reported
as a median, because the spread between identical runs on this device is 27-36 MB
and several single-run "improvements" earlier were inside it. Rendering is a
verdict from `tests/device/run.sh`, not a screenshot.

## Closed, with the number that closed it

**Joined emoji compose into one glyph.** A grapheme cluster here was
CoreFoundation's idea of one, and this CoreFoundation is from 2012:
`kCFStringComposedCharacterCluster` knows nothing of the ZWJ sequences Unicode
added from 2015 on, so a family or a profession was shaped as its parts - a
beacon caught the joiner arriving at the shaper alone, in the page's text font.
The character, caret and deletion iterators use the ICU backing now, which is
what every non-Cocoa port uses and which this port builds at version 74. An
astronaut is one 26px glyph where it had been two.

**The system font answers font-weight.** Two faults: `kCTFontWeight*` are
declared `CGFloat` and the compatibility layer defined them as CFStrings, so
every rung was a pointer read as a float; and the numeric weight trait is an
iOS 7 mechanism, so the request also goes through
`CTFontCreateCopyWithSymbolicTraits`. `-apple-system` at 700 is 34.2px against
33.0 at 400, and draws bold.

**Thirteen of the eighteen feBlend modes were erased.** This port re-enables NEON,
which upstream disables on iOS, and `FEBlendNeonApplier` predates the CSS blend
modes: it implements five and writes transparent black for the rest.

**Rounded corners were parabolas** - both bezier control points sat on the corner
vertex in the shim - and uneven ones landed on the wrong corner. WebKit's own
beziers draw them now.

**Gradients fading to transparent went through grey.** Premultiplied
interpolation travels in an options dictionary that this CoreGraphics has no
entry point for; the engine's sampling path does it correctly instead. Measured:
the middle of red-to-transparent is 255,0,0.

**Purgeable decoded images: measured, and left off.** 160.9 MB against 203.4 MB
after four sites - a real 42 MB - and the page that draws one image six hundred
times cropped takes the process down. The measurement and the switch to
reproduce it are in the code.

**`useUnlinkedCodeBlockJettisoning`**: no measurable win, returned to upstream's
default rather than kept on faith.

Smaller, all measured or read from the code: a colour font is taken at its word
about having colour glyphs; variation axes are not read on a CoreText that has
none; `vDSP_vaddi` adds vectors instead of returning success and writing nothing;
a blob bind that answered SQLITE_OK while binding nothing is gone; two feature
readers no longer decide from uninitialised memory; the icon writer uses a colour
space that exists.

## In progress

### Pinning `CompositingPolicy::Conservative`

The first of the two remaining memory levers from the history sweep. Under this
policy a no-op 3D transform and a bare `will-change` stop promoting an element to
its own layer, and each layer avoided is a 640x960x4 backing store - 2.4 MB - on
a device the system takes away at about 280 MB. It is one line in
`RenderLayerCompositor::updateCompositingPolicy`, and upstream tried exactly this
for 512 MB machines in 2015 and rolled it back for discussion rather than for a
measurement.

Built and deployed; three cold runs of four heavy sites are running. The bar it
has to clear is the noise band: the spread between identical runs here is
27-36 MB, so anything smaller than that is not a result. Baseline to beat, from
this build's own measurement earlier tonight: first page 100.7 MB, after four
sites 157.4 MB.

What is deliberately not claimed either way: scrolling. There is a scroll
benchmark in `scripts/bench-native.sh`, but it drives the standalone app rather
than the substituted Safari, so it does not answer the question for this build,
and a screenshot cannot. If the memory gain does not clear the noise band the
policy comes back out and the question never arises.

**Result: not a lever, and it came back out.** Three cold runs with the policy
pinned: first page 101.0 / 101.1 / 105.7 MB, after four sites 220.7 / 131.7 /
163.6 MB - median 101.1 and 163.6 against this build's own 100.7 and 157.4. The
spread of the runs is 90 MB wide and the medians are inside each other's noise,
so there is nothing here to keep and nothing to argue about; the line is gone.
No new crashes and no memory kills during the runs.

Worth recording why it is plausible and still empty: the layers this policy
declines to promote are the ones a page asks for with `translateZ(0)` and
`will-change`, and the sites measured here may simply not create many of them -
or the compositor was already declining them under the port's permanent strict
memory policy, which would make the pin a no-op by construction.

### `GSFontPurgeFontCache` - closed by a probe, not by an argument

The sweep suggested the empty shim for it might be hiding a real GraphicsServices
function of exactly this vintage, which would be a free font-cache purge under
memory pressure. A three-line `dlsym` probe on the device settles it:
`GSFontInitialize` and `GSFontCreateWithName` are both there, and
`GSFontPurgeFontCache` is **not** - not through `RTLD_DEFAULT` and not in the
GraphicsServices binary. The shim is honest and there is nothing to call.

### The disk image cache: not attempted, and the arithmetic is why

The sweep's second memory lever was `ENABLE(DISK_IMAGE_CACHE)`, removed from
WebKit in 2014 - it mapped encoded image bytes from a file for WebKit1 on iOS,
which is this port's architecture. The pieces to rebuild it are all in the tree
and none of it would be invention: `FileSystem::mapToFile`,
`SharedBuffer::createWithContentsOfFile`, and WebKit's own
`CachedResource::tryReplaceEncodedData`, which is exactly the hook the Cocoa
`DiskCacheMonitor` uses when CFNetwork reports a response has become
file-backed. (That notification is one of the things this OS does not have -
`_CFCachedURLResponseSetBecameFileBackedCallBackBlock` is in the engine's
unavailable list - so the port would have to trigger it itself, on a memory
warning, the way the deleted `flushCachedImagesToDisk` did.)

It is not being built, because of the ceiling rather than the effort: this port
caps `cacheTotalCapacity` at 8 MB, so the whole encoded-bytes bucket the change
would move out of dirty memory is at most 8 MB - well inside the 27-36 MB spread
between identical runs. It could not be shown to work even if it did. If the
resource cache is ever raised, this becomes worth doing, and the pieces above are
the recipe.

### The SVG-image filter defect: what a night of beacons established

Three checks in `tests/device/svg-image-filters.html` fail: a pixel-reading
filter inside an SVG, loaded through `<img>` and drawn to a canvas, comes out one
gamma encode too bright - `92` reads as `156`, `192,64,64` as `225,137,137` -
and the page sometimes ends in SIGSEGV. The two checks beside them are the
discriminator and both pass: the same SVG with no filter, and with `feOffset`,
are exact.

Ruled out, each by a measurement rather than an argument:

- **The linear-light work.** Compiled out; both symptoms unchanged.
- **Colour space tags.** Beaconed at the effect: source, result and buffer are
  all linearRGB, and no conversion runs between them.
- **Any conversion of this port's own.** Beacons in
  `FilterImage::transformToColorSpace`, in the bitmap backend's transfer, and in
  `convertImagePixelsAcrossSRGBAndLinearSRGB` - **none of them fires on this
  path at all**, on a page reduced to a single filtered SVG image.
- **CoreGraphics matching.** linearRGB and sRGB are the same `CGColorSpace` on
  this port, so there is nothing for CG to convert between.
- **Filters in general, and the arithmetic.** `feOffset` is exact, and every
  blend mode measured through a canvas is correct.

So the encode is applied by something on the SVG-image rasterisation path that
predates tonight's work, and no beacon of mine sits on it. Three repairs were
tried and all three are recorded as dead ends: copying the borrowed source buffer
with the filter allocator (wrong resolution scale), with `ImageBuffer::clone()`
(crashed), and restoring the source buffer's colour space after the chain
(changed no number). The next person - or the next session - should start by
beaconing `SVGImage::nativeImage` and the canvas `drawImage` path rather than the
filter machinery, which is where tonight's evidence points.

### Also closed by measurement, negatively

`mix-blend-mode: hue | saturation | color | luminosity` on an element draws
unblended, while the identical blend through a canvas is correct (hue of
64,128,192 over 224,160,32 gives 105,180,255). So CoreGraphics implements all
eighteen modes and only the element path fails: those four are handed to a layer
as CoreAnimation filter types this QuartzCore does not have, and a composited
layer blends only through the compositor. Declining to composite such layers at
`canBeComposited` blanked every page and crashed the browser thirteen times; the
attempt is recorded so it is not repeated, and the honest description is a
platform limit on composited layers rather than an engine defect.

Wide-gamut colour, from the same sweep, turned out not to be broken at all:
`color(display-p3 0.4 0.7 0.2)` paints 70,181,0, `color(rec2020 ...)` 0,193,25,
and `lab()` its own answer - all converted, none passed through raw.

## The image crash, diagnosed

The suite went back to 21 pass / 3 fail once the modern emoji font was
reinstalled - it had been swapped back to the stock one during the font
measurements, which is all the six extra failures were.

Then the crash that has been called "a broken image kills the browser" all day
turned out to be neither about broken images nor about the disk cache monitor:

- With the monitor gated out the process still died, and faster.
- A page of twenty large JPEGs dies too, with no crash report at all - that one
  is jetsam, the page carries 15 MB of encoded bytes.
- The 404 page dies with SIGSEGV on the web thread, and symbolicating the stack
  against the built framework (rather than reading the nearest exported symbol,
  which had pointed at BitmapImage::create for hours) gives:
  didReceiveData -> CachedImage::updateBufferInternal -> BitmapImage::dataChanged
  -> BitmapImageSource::setData -> decoder() -> a virtual call through slot 0x64
  that lands in BitmapImageSource::size, faulting on the load of the decoder
  field.

A virtual call arriving at a function of a different class is a vtable layout
disagreement. ImageDecoder's virtuals sit behind four build flags, so a stale
object file shifts every slot after them - the partial-build trap, in a place
that only crashes once image data is streamed. A clean rebuild is running.

Two process defects found on the way, both fixed:

- deploy-engine.sh pushed the staged copy without staging it, so three deploys
  carried an older binary and the tests measured code that was not there.
- The measurement of file-backed encoded image data was worthless for the same
  reason plus a second one: the mapper only runs under memory pressure, which
  twenty images do not reach, so both arms of the A/B were the same code doing
  nothing. It is in the tree with a forced-release switch to drive it, waiting
  for a device that does not crash on an image page.

## The crash is closed, and what the file-backed images cost

`HAVE_AVASSETREADER` is off on this port now. The evidence chain, for the record:

1. The upgraded crash handler prints the program counter and the faulting
   address, which the backtrace never did - its innermost entry is a return
   address, so every earlier symbolisation named the wrong function.
2. With that, the fault was a call through a vtable slot holding zero, on an
   object that was not a decoder at all.
3. A beacon on each branch of `ImageDecoder::create` showed why: for a response
   whose MIME type is not a supported image type (a 404 body is `text/plain`),
   the engine asks the registered factories, and the only factory is
   `ImageDecoderAVFObjC` - whose implementation file this port excludes from the
   build. All four of its entry points linked to the same stub: `canDecodeType`
   answered `64449028`, `createImageDecoder` returned `0x7`.

Verified: the repro page and a page of twenty large JPEGs both live past 75
seconds; the suite is back to 21 of 24, with the three SVG-filter failures that
were already known.

### File-backed encoded image data: 10.6 MB, and not shippable yet

Hooked where the historical disk image cache hooked it - at load completion, the
bytes written on a work queue and swapped in through
`CachedResource::tryReplaceEncodedData` - the twenty-image page measures:

| | dirty | malloc |
|---|---|---|
| without file backing | 48.6 MB | 13.00 MB |
| with file backing | 38.0 MB (two runs identical) | 13.00 MB |

So the saving is real and it is 10.6 MB on this page. It is not committed,
because the same page then dies with SIGABRT out of an uncaught exception
rethrown from the run loop - three runs out of three, where the page survived 75
seconds without the change. The work is saved as
`wip/file-backing-at-load.patch`; the next step is to find that exception (the
suspects are the work-queue hop itself and the `WebThreadRun` install), not to
re-measure the saving.

## The filter brightness is closed too: 24 of 24

The arithmetic named it: 192 read back as 225 and 64 as 137 is exactly
`sRGBEncode(v)` applied to a value that was already encoded - one extra encode,
not a filter that computes wrongly.

The engine carries the fix already, under `USE(CAIRO)`, in three places: the two
that choose the colour space of a filter's source buffer, and the one that
converts that buffer into the filter's operating space before the chain runs.
Cairo takes the sRGB-and-convert path because it cannot convert while painting.
This CoreGraphics cannot either - it matches by primaries and ignores transfer
functions, so linearRGB and sRGB are one and the same `CGColorSpace` here - and
it was on the other path, where the source is tagged linear and the painting is
expected to convert. Nothing converted, and the closing conversion back to sRGB
encoded a second time.

With this port on Cairo's path: saturate in linear light 109 (specified 109),
saturate in sRGB 92 (92), identity exact. **The suite is 24 of 24, twice.**

Worth recording as a lesson rather than a fix: the earlier finding that
"compiling the linear-light conversion out changes nothing" was true and it sent
me the wrong way for a week. It changed nothing because the conversion was never
reached, not because it was innocent of the symptom.

## The ten megabytes are in

File backing is committed. What changed from the attempt that crashed three
times out of three: nothing in its own design - the same work queue, the same
`tryReplaceEncodedData` - but the build it was measured on now also carries the
decoder fix, and the page it was killing was being killed by the decoder stub,
not by the mapping. Beacons on each step of the mapping show the whole sequence
completing: queued, written, mapped, installed on the web thread, resource
found.

Final numbers, three cold runs each:

| | dirty | malloc |
|---|---|---|
| without | 48.6 MB | 13.00 MB |
| with | 37.8 / 41.2 / 38.0 MB, median 38.0 | 13.00 MB |

Three survival runs of 75 seconds, no leftovers in /tmp, suite 24 of 24.

## Non-separable blend on elements: narrowed, not closed

Four measurements, three of which remove a suspect:

- A standalone CoreGraphics probe on the device blends hue correctly, both by
  direct fill and through a transparency layer: 105,180,255 either way. The
  platform is not the problem.
- The engine's software path runs for the element and asks for the right mode.
- Re-applying the mode immediately before `CGContextEndTransparencyLayer` makes
  no difference, so it is not about when CG captures the mode. That attempt is
  backed out; it is saved as `wip/blend-at-end.patch`.
- The layer path was never observed setting a blending filter.

So the remaining explanation is that the blended box is composited into its own
backing and blends against nothing. The suite now has a numeric way to check it -
screenshot plus pixel read - which it did not have this morning.

## What the file backing is worth on the real web: almost nothing

The ten megabytes are real, and they are real on a page made of twenty 750 KB
photographs. On ordinary pages the mechanism barely fires. Measured directly -
counting the bytes it actually moves, which is immune to the dirty-memory noise
that makes a single cold run on a live site meaningless:

| page | images mapped | bytes moved |
|---|---|---|
| en.wikipedia.org/wiki/IPhone_4S | 0 | 0 |
| github.com/WebKit/WebKit | 1 | 78 KB |
| soundcloud.com | 2 | 125 KB |
| google.com/search | 0 | 0 |

Lowering the threshold from 16 KB to 4 KB changes that to 20, 83 and 130 KB -
still noise, for three times the files. The threshold stays at 16 KB.

The five-site dirty figures with and without the mechanism confirm it from the
other side: 67.1/106.0/98.8/95.6/33.7 MB against 65.1/104.9/92.4/102.4/33.9 -
401.2 MB against 398.7 MB in total, which is the run-to-run spread and nothing
else. One cold run per site cannot resolve a difference this small, and the
direct count says there is no difference to resolve on these pages.

So the honest statement is: **worth 10 MB on image-heavy pages, worth kilobytes
on a news site, and free when it does not fire.** It stays in, and the claim in
the commit message should be read as what it says - twenty images carrying 15 MB
of encoded bytes - not as a figure for the web at large.

None of the five sites crashed, which is the other thing this pass was for: the
image-decoder fix holds on the real web.
