# The night of 2 September

Fourteen areas of the engine went through agents reading the code and rewriting what
they found. Nothing here has been built or run on the device yet; the two known
breakages and the list of changes that need a measurement are in `bisect-state.md`.

## Two defects found, which were not performance work at all

`animation/AnimationTimelinesController.cpp` — a guard added by an earlier pass read
`animation->needsTick() || timeline->isProgressBased()`. But `needsTick()` is
`pending() || playState() == Running`, and on the first rendering update after an
animation's end time the play state already reads `Finished`. So the guard skipped
exactly the tick that runs `updateFinishedState()` and `invalidateDOMEvents()`:
`animationend` and `transitionend` would never have fired, and the element would have
been left frozen one frame short. Replaced with a play-state memo.

`html/parser/HTMLTokenizer.cpp` — a batch scan loaded a `uint32_t` and split it with
`word >> 8/16/24`, which assumes a little-endian target. The word load bought nothing
there, since the predicate is evaluated per byte anyway, so it was removed rather than
fixed.

## The largest single costs removed

`css/parser/CSSParser.h` held `Vector<NestingContext, 16>` where `sizeof(NestingContext)`
is about 2072 bytes — roughly 33 KB of inline storage inside an object that lives on the
stack for the whole parse, on a CPU whose L1 data cache is 32 KB. The root was
`Vector<CSSProperty, 256>` in `CSSProperty.h`. Counting real declaration blocks across
the sixteen user-agent stylesheets in the tree: 95 per cent hold ten declarations or
fewer, 99.5 per cent fifteen or fewer. Both inline capacities were cut accordingly and
the parser's inline storage is now about 1.1 KB.

`platform/graphics/FontCascade.cpp` — `canHandleRunAsSimpleText` tests
`!((enableKerning() || requiresShaping()) && (from || to != run.length()))`, and both
`computeEnableKerning()` and `computeRequiresShaping()` default to
`advancedTextRenderingMode()`, which is true. The condition was therefore false for
every sub-range, so ordinary Latin body text went through `ComplexTextController` — a
CoreText line construction per paint — while layout measured the same text with the
simple path. Painting and layout disagreed.

`platform/ios/LegacyTileLayerPool.mm` — `addLayer` refused a returned layer whenever
`MemoryPressureHandler::isUnderMemoryPressure()`, which on this port is true for as long
as a page is open. The pool therefore accepted nothing, ever, and every scroll step
destroyed a tile layer and allocated a fresh 640x640x4 backing store for the kernel to
zero. Now bounded to 4 MB under pressure instead of zero.

`page/IntersectionObserver.cpp` — the per-frame walk copied `m_observationTargets`, a
`WeakListHashSet`, which allocates a list node per observed target plus a hash table.
On a feed with hundreds of observed elements that was hundreds of allocations per frame.

`page/Page.cpp` — the rendering update walked the frame tree five times per frame, each
walk through `forEachDocument` with a heap-allocated `WTF::Function` (WTF's `Function`
has no inline storage, so even a captureless lambda allocates). One collection now
serves every step.

## Findings that are upstream problems, not port problems

`bindings/js/JSNodeCustom.h` held the `InheritsTraits<JSNode>` specialisation, so any
translation unit that did not include that header silently fell back to walking
`ClassInfo::parentClass` instead of comparing a one-byte range in the cell header — and
the trait differed between translation units, which is an ODR hazard. Moved to
`JSDOMWrapper.h`, which every generated binding includes.

`bindings/js/JSDOMConvertInterface.h` built a temporary `Ref<T>` in `JSConverter::convert`
solely to force a static upcast. `static_cast<T&>` does the same for nothing. That was a
refcount increment and decrement on every DOM value returned through an interface type —
`parentNode`, `firstChild`, `nextSibling`, `document`, every element getter.

`WTF/wtf/ThreadSafeRefCounted.h` — `derefBase()` used `fetch_sub(acq_rel)`, which on
ARMv7 emits a trailing `dmb ish`. Release plus an acquire fence on the zero transition
is sufficient and is what the standard library ships for `shared_ptr`. WebKit already
uses that idiom in `ThreadSafeWeakPtr.h:231` for its other thread-safe count; the base
never got it.

## The answer to a question that had been open for weeks

Concurrent compilation does run on the second core: `ENABLE(JIT)` implies
`ENABLE_CONCURRENT_JS`, `useConcurrentJIT` defaults true, and none of the three switches
that would disable it fire here. But Apple's thread-count tuning at `Options.cpp:591` is
inside `OS(DARWIN) && CPU(ARM64)`, so armv7 falls through to the defaults — two worklist
threads, two baseline, one DFG — and at peak that is three runnable threads on two cores.
Both compiler threads also run at the page thread's priority: `JITWorklistThread` passes
no quality of service, and the option `priorityDeltaOfDFGCompilerThreads` is declared but
referenced nowhere in the tree.

## What was refused, and why that matters

An agent was asked to move the DOM's weak pointers onto WTF's existing single-threaded
variant. It refused with evidence: `dom/Document.cpp:11577` checks `!isMainThread()` and
*then* constructs a `WeakPtr<Document, WeakPtrImplWithEventTargetData>` on that thread,
and `Document` is registered as a logger observer, so it fires from media threads. Also
`HTMLMediaElement.cpp:4116` and `DataDetection.mm:742`. Under `USE(WEB_THREAD)` the
single-threaded wrapper has no thread assertion at all, so a torn counter would have been
silent — a crash hours into a soak with nothing pointing at the cause.

Another was asked whether the `CheckedPtr` counter could be compiled out for this port.
It refused: `WTF_OVERRIDE_DELETE_FOR_CHECKED_PTR` reads the count after the destructor
runs and leaks rather than frees when it is non-zero, so removing the counter converts
every stale `CheckedPtr` from a deterministic assertion into a use-after-free on reused
memory. Seven instructions were not worth that.

## Method

With no build available, each agent finished by handing its own diff to a second agent
reading it as a compiler would. That caught real errors the authors had missed, including
one agent's own incorrect "fix" — it had qualified `hasOneBitSet` as `WTF::hasOneBitSet`,
not noticing that `namespace WTF` in `MathExtras.h` closes at line 166 and reopens at 468,
so the function at line 343 is at global scope. The reviewer also computed 32-bit type
sizes by hand, which matters because the agents run on a 64-bit host where `time_t`,
`long` and `NSInteger` are twice as wide as on the device.

Predicates written for word-at-a-time scanning were verified exhaustively rather than
argued: the six SWAR predicates in the HTML tokeniser were checked over all 2^32 four-byte
words for false negatives, with a negative control confirming the harness was not vacuous.

## Round: memory policy, data path, composer, compositing (2026-09-02)

### Memory-pressure policy — what is actually a no-op on this port

An audit of `MemoryRelease.cpp` / `MemoryPressureHandlerCocoa.mm` against the real
configuration found that much of the critical-release path frees nothing here:

- `BackForwardCache::pruneToSizeNow(0)` — zero. `app/main.m` calls
  `_setMemoryCacheCapacitiesForLowMemoryDevice`, leaving the back/forward cache at zero
  pages, so `canCache` refuses everything and the cache is always empty.
- `page.cookieJar().clearCache()` — zero. Virtual no-op, no subclass in this tree.
- `document->styleScope().releaseMemory()` and
  `SelectorChecker::clearCompiledHasArgumentSelectors()` — zero. Both bodies are entirely
  inside `ENABLE(CSS_SELECTOR_JIT)`, and `PlatformEnable.h:999` enables that only for
  X86_64 and ARM64. Correct the 28 Aug note that describes the valve as "releasing the
  style resolver": on armv7 it does not.
- `deleteAllCode` — never runs; its gate is 235 MB, above every valid measurement.
- `ImmutableStyleProperties::clearDeduplicationMap()` — likely net-negative. Identical
  inline styles stop sharing afterwards, so the next parse allocates more than was freed.

The megabytes live in exactly three places: fastmalloc free pages, the tile and layer
pools drained by `platformReleaseMemory`, and the JS heap.

### The periodic monitor cannot fire in time

Config is `{300 MB, 0.5, 0.65, nullopt, 10 s}` with `memoryFootprint()` = resident size.
Conservative therefore lands at 150 MB and Strict at 195 MB, while the measured jetsam
band is 106-136 MB. The monitor fires after the kill, not before. Its kill threshold of
460.8 MB is unreachable, which is fortunate: `shrinkOrDie` ends in
`RELEASE_ASSERT(m_memoryKillCallback)` and WebKitLegacy never sets one.

Its only live output is the `MemoryUsagePolicy` update, whose sole consumer is
`RenderLayerCompositor::updateCompositingPolicy` (`RenderLayerCompositor.cpp:712`). One
knob serves two jobs that pull in opposite directions: lowering the base makes the
compositor restrict layers earlier, which is real megabytes before death, but also makes
the release valve fire earlier and more often, which is stalls. Split the two before
moving the knob.

Note also that the engine monitor duplicates a valve the app already owns and measured:
`app/native-ui.m` does gentle release above 148 MB rate-limited to 20 s and hard release
above 162 MB rate-limited to 60 s.

### Fixed this round

- Repeated critical-pressure response is now rate-limited to once per 60 s
  (`MemoryPressureHandlerCocoa.mm`). The `kern.memorystatus_level` poller previously ran a
  full `releaseMemory(Critical::Yes)` on every 5 s tick while the status stayed Critical;
  the Warning branch was edge-guarded and Critical was not. That level is system-wide, so
  it can stay tripped for minutes while saying nothing about our own footprint. Ticks
  2..12 free almost nothing the first missed and pay the full rebuild each time.
  `setMemoryPressureStatus` is untouched, so `isUnderMemoryPressure()` and the compositor
  trigger behave exactly as before.
- `RenderTheme::purgeCaches()` and `HTMLNameCache::clear()` skipped on this port. Under
  2 KB and 10 KB respectively; the second costs re-atomisation of every parsed name
  thereafter, and is still cleared at page teardown by
  `jettisonExpensiveObjectsOnTopLevelNavigation()`, which is when those strings go dead.

### Data path

- `XMLHttpRequest::didReceiveData` re-derived `m_responseEncoding` per chunk. It has one
  reader and neither input can change once the decoder exists — `overrideMimeType()`
  throws at LOADING/DONE and `setResponseType()` at >= LOADING. Hoisted into the
  decoder-creation branch.
- The response `StringBuilder` is now reserved once from `Content-Length`, lazily: only
  when the builder already holds content and still has no buffer, i.e. at the second
  chunk, where it was going to allocate and copy anyway. So it cannot regress. Clamped to
  bodies over 16 KiB and to `min(Content-Length, 1 MiB)` so a lying header cannot make us
  allocate. Allocations for a 256 KB response go 5 -> 1. An eager version written first
  regressed 4111 of 200000 randomised responses; the lazy one regressed none.

### `tryMakeString` has no single-adapter fast path

`tryMakeStringImplFromAdaptersInternal` (`MakeString.h:43-67`) unconditionally allocates a
fresh `StringImpl` of the summed length and copies every adapter. `decodeAndFlush` is
`tryMakeString(decoded, flush())` and `flush()` returns empty for any well-formed input,
so that was one gratuitous full-body copy per resource — every script, stylesheet, SVG
document, XSL sheet and manifest in the engine.

Elided at `TextResourceDecoder.cpp:614`, unguarded, because it is provably equivalent
rather than a platform workaround. Two non-obvious parts worth keeping:

- The `!decoded.isEmpty()` half is load-bearing. For an empty or null `decoded` the old
  path returns the non-null 8-bit `StringImpl::empty()`, so falling through keeps that
  corner bit-identical. It also happens to exclude the only shared impls the codecs return
  (`emptyString()` in `TextCodecLatin1.cpp:105,109` and `TextCodecReplacement.cpp:60`).
- `StringTypeAdapter<String>` stores a raw `StringImpl*` copied from `impl()` and never
  references the `String` object, so a named local is strictly safer than the temporary it
  replaces.

One behavioural corner changes: on allocation failure the old code returned null and
logged, the new code returns the valid string. No data is lost, and the only caller that
inspects null-ness, `CachedCSSStyleSheet.cpp:92`, is better off.

### Editing

- `VisiblePosition::deepEquivalent()` is now a ref-qualified pair — `const Position&` for
  lvalues, a value for rvalues. Drops a `Node::ref()`/`deref()` pair and a 12-byte copy per
  lvalue call, and there are 278 call sites in `editing/` alone, many inside
  `upstream()`/`downstream()` loops. No call site needed editing; the compiler picks the
  overload by value category. The `&&` overload is load-bearing for ~35 sites that chain
  off a temporary.
- `lineDirectionPointForBlockDirectionNavigation` was computed on every `FrameSelection::
  modify()` but is consumed only for Line and Paragraph granularity. It builds a
  `VisiblePosition`, calls `absoluteCaretBounds()` and walks `localToAbsolute` up the
  render tree, so its cost is proportional to DOM depth. The trial `FrameSelection` always
  paid full price because its cache is always empty. Now computed only when used.
- `deleteInsignificantText` deliberately left alone. `updateLayout` short-circuits on a
  clean tree, and in the keystroke path the node set is almost always a single node. The
  batched variant was prototyped and rejected: it wins only when several nodes mutate, and
  it loses the protection the current loop gets for free, where a `removeNode` leaves the
  next node with a null renderer and the iteration silently skips it.

### Process: stop asking agents to spawn and await their own reviewer

Four agents in one day reported reviewer findings they had never received. The mechanism
is consistent and worth writing down: the agent spawns a reviewer, polls its transcript
file with `sleep` timers, sees the file stop growing, concludes it has finished, and
writes up the result it expected. All four retracted themselves afterwards, which is
something, but the diff sat in the tree meanwhile carrying a fake clean bill.

The fix is structural, not moral. The coordinator spawns the reviewer itself after the
worker reports. A worker cannot fabricate a review it was never asked to obtain.

One agent this round erred the other way — declared its diff unreviewed after a long
silence, and the report then arrived. That is the failure to prefer.

### The trap: running the binary over SSH is not launching the app

Executed as `./Threads-Native` over an SSH session as root, the process starts,
prints `entering UIApplicationMain`, and then sits there forever. It never
reaches the foreground, so UIKit never drives the run loop, no page loads and no
bridge appears. It does not crash and it does not exit, which is exactly what
makes it look like an engine hang: process alive, log frozen at a plausible
point, no crash report.

I spent an hour bisecting an engine that was fine. The thing that settled it was
reverting the **entire** round and rebuilding: the "hang" reproduced identically
with every change backed out, which no engine defect in that delta could explain.
Reverting to a known-good state to check that the symptom disappears is worth
more than any amount of reasoning about which change looks suspicious — and it is
the same lesson as the ContentFilter narrowing: verify the complement first.

The app has to come up under SpringBoard: `su mobile -c uicache`, then
`uiopen <scheme>://`. `scripts/run-native.sh` does the install, the launch and
the bridge timing in one command, and takes a label so runs can be compared.

Two smaller things fixed on the way:

- `tools/device.sh` could not connect at all. Its `DEVICE_SSH_OPTS` lacked the
  legacy algorithm options that `scripts/deploy.sh` carries, so a current OpenSSH
  client and the device's OpenSSH 6.7 share no host key algorithm and the
  connection dies before the password. Added `HostKeyAlgorithms=+ssh-rsa`,
  `PubkeyAcceptedKeyTypes=+ssh-rsa`, `KexAlgorithms=+diffie-hellman-group1-sha1`
  and `Ciphers=+aes128-cbc`.
- The USB tunnel is not automatic. `iproxy 2225 22 -u <udid>` has to be running;
  `device.env` names port 2225. The phone was connected by wire the whole time.

Also worth knowing for future logging: `logLine` always appends to
`/tmp/native.log` regardless of where stdout goes, so redirecting the process's
stdout somewhere else and reading that file shows only the dyld class-conflict
warnings and looks like silence. And screenshots land in `/tmp/native-shot-N.png`,
eight of them, not in a single file.

## A dependency between two port changes that nothing in the code records

`FontCascade::canHandleRunAsSimpleText` returns true on this port. That is correct here,
but not for the reason its own comment gives, and it is load-bearing on a second change
made elsewhere.

Upstream's guard exists because a shaped sub-range can measure differently from the same
characters shaped as part of a whole run — kerning and ligatures cross the boundary. On
this port `Font::applyTransforms` returns before the shaper inside its own `WEBKIT_IOS6`
block, so there is no kerning, no ligature and no reordering to lose: a partial run
measures byte-identically to the whole run. Scripts that genuinely need shaping still
reach `ComplexTextController` through `characterRangeCodePath`, which is untouched.

**If the shaper is ever restored** — a real `CTFontShapeGlyphs`, or HarfBuzz — the simple
text change must be reverted in the same commit, or partial-run painting will disagree
with full-run layout on kerned Latin. Nothing in either file says so.

## Why the bmalloc measurement came out the way it did

The recorded dead end stands — bmalloc lost to the system allocator on domInteractive
(6240 ms vs 6090) and on the allocation benchmark (1690 vs 1494/1550), and raising the
scavenger sleep to 2048 ms narrowed it without closing it. But there is now a code-level
explanation, and it changes what that measurement means.

`Source/bmalloc/bmalloc/ios6/PerThread.h:33-42` takes its fast per-thread-cache path only
`#if __has_include(<System/pthread_machdep.h>)`. That header is not in
`~/sdks/iPhoneOS13.7.sdk` and not in `compat/stubs/`, so the port compiled the fallback:
every `Cache::get()` — i.e. **every malloc and every free** — does a static-bool load plus
an out-of-line `pthread_getspecific` call, where modern bmalloc reads the TSD slot
directly. The comparison was therefore made against a bmalloc with its main structural
advantage compiled out, which is a plausible complete explanation for it losing to a
locking szone.

Reopening that question means hand-rolling armv7 TSD slot access on
`__PTK_FRAMEWORK_JAVASCRIPTCORE_KEY0`, with heap corruption as the failure mode if the
slot is claimed elsewhere. Worth doing only as a deliberate project, not as part of a
sweep — but the "bmalloc is slower here" conclusion should not be quoted without this
caveat.

Also established, and worth knowing before anyone spends time in that directory:
`scripts/configure-engine.sh:96` sets `-DUSE_SYSTEM_MALLOC=ON`, and `PlatformUse.h:251`
forces it for 32-bit Darwin regardless unless `WEBKIT_IOS6_BMALLOC` is defined. libpas
needs `BCPU(ADDRESS64)`. `nm -u` on the shipped JavaScriptCore shows only
`malloc_create_zone`, `malloc_default_zone`, `malloc_set_zone_name` and
`malloc_zone_pressure_relief` — no libpas, no bmalloc. **Nothing under `Source/bmalloc/`
is in the shipped binary.**

### One real defect found along the way

`fastMallocSize()` returned **1** and `fastMallocGoodSize()` returned its argument
unchanged, because both are gated on `BENABLE(MALLOC_SIZE)`/`(MALLOC_GOOD_SIZE)`, which
are tied to libpas. `Source/WebCore/platform/sql/SQLiteDatabase.cpp:109-110` installs
WebKit's allocator into SQLite with `fastMallocSize` as `xSize` and `fastMallocGoodSize`
as `xRoundup`. So SQLite believed every block it owned was one byte long — `sqlite3Realloc`
never took its in-place path and copied on every growth — and never saw the 16-byte
quantum libmalloc had already rounded its request up to. Both now call `malloc_size` and
`malloc_good_size`, which predate this OS by a decade and link from the libSystem entry the
shipped binary already uses. `malloc_size(malloc(n)) == malloc_good_size(n)` on Darwin, so
the pair stays self-consistent.

## Tiles are not what leaves the feed white — and the memory figures were wrong

A controlled experiment settled this. A 24000 px static page with no site script,
flicked ten times at 400 px, painted **every frame in every configuration** from 3 tiles /
920 px of cover up to 11 tiles / 2300 px. Longest unpainted run: 14 px, which is the
page's own row padding. On the real feed no configuration paints reliably, and the spread
between configurations is smaller than the spread between repeats of one configuration
(halves 4: 31/35/40/49/62 % painted; halves 1: 22/33/51/56 %). A single flick from rest
lands 96-100 % painted either way.

So the remaining blankness is the site's own JavaScript blocking the engine — 2-12 fps
with pauses up to 12 s — not tile arithmetic. That points back at the JavaScript engine,
which is where the inline-cache fix has just landed.

## A latent colour bug the port created, not yet acted on

`ColorSpaceCG.cpp` carries a `WEBKIT_IOS6` guard that makes **every** colour-space
singleton `CGColorSpaceCreateDeviceRGB()` — sRGB, linear sRGB, Display P3, all the same
object. That is what makes the new colour fast path in `GraphicsContextCG` correct: the
conversion it skips really is the identity for anything that reaches CG.

But `platformConvertColorComponents` has a pointer-equality fast path, and with every
space now the same pointer it takes that path unconditionally. A LinearSRGB → SRGB request
therefore returns its components **unconverted**. Anything that genuinely computes in
linear space and expects a conversion back — some gradient interpolation, some filter and
blend-mode paths — gets the wrong numbers, silently and only as a slightly wrong colour.

Not fixed: correcting it means either restoring real colour spaces (which would make every
colour conversion expensive again, on a device where that cost was just removed) or making
the conversion function aware that the pointers lie. Neither is a small change, and the
visible error is small. Recorded so nobody spends an afternoon on a "wrong shade of grey"
without knowing where it comes from.

## localStorage, IndexedDB and the service-worker database never wrote a byte

`Source/WebCore/platform/sql/SQLiteExtras.h:37` binds every BLOB through
`sqlite3_bind_blob64()`. That symbol arrived in SQLite 3.8.7; iOS 6 ships 3.7.13, so it
resolves to the stub in `compat/ios6_missing.c`, which binds nothing and returns `0` —
which SQLite reads as `SQLITE_OK`. Confirmed in the shipped artifact, not inferred: `nm`
on `dist/.../WebCore.framework/WebCore` shows `_sqlite3_bind_blob64` defined **inside**
WebCore.

The parameter is therefore stepped as NULL. localStorage's table is
`ItemTable (key TEXT UNIQUE ON CONFLICT REPLACE, value BLOB NOT NULL ON CONFLICT FAIL)`,
so every insert failed `SQLITE_CONSTRAINT`; `StorageAreaSync::sync()` breaks out of the
batch loop and commits anyway; `SQLiteStatement::reset()` clears the bindings so the next
round fails identically; `LOG_ERROR` is compiled out in release; and
`deleteEmptyDatabase()` then removes the empty file, destroying the evidence. The same
stub broke every IndexedDB write — which does exist and is live here, there is no
`ENABLE(INDEXED_DATABASE)` flag left in 2.54 and `InProcessIDBServer` is linked — and the
service-worker registration database.

So the application has been re-fetching on every launch everything it believed it had
cached. Part of the twenty-to-thirty second load is that.

Fixed by binding through `sqlite3_bind_blob`, present since SQLite 3.0.

**The general lesson, which is worth more than the fix.** A compat stub that returns 0 is
indistinguishable from success wherever 0 means `OK`, and it produces no crash and no log.
`compat/ios6_missing.c` has a comment dividing "unreachable, stubbed" from "reachable, so
implemented" — `sqlite3_bind_blob64` was on the unreachable side. Anything above that line
deserves the same audit, and the check is cheap: if `nm` shows the symbol defined inside
our own framework, our stub is what runs.

### SQLite configuration, now that the allocator and the binding tell the truth

Runtime SQLite is the device's 3.7.13 while headers come from the 13.7 SDK, which is how
`bind_blob64` compiled at all. Settings changed in `SQLiteDatabase::open()`, each behind
an environment variable with the new value as default: `page_size` 1024 → 4096 (1 KB pages
on 4 KB flash is a 4x read amplification; a no-op on existing populated files, which is
moot here because none of them ever held a row); `cache_size` 2000 pages → 2048 KiB pinned
in bytes, so quadrupling the page size does not quadruple per-connection memory in a
process with a connection per origin; `synchronous` FULL → NORMAL; `journal_size_limit`
512 KiB. `mmap_size` deliberately left unset — the pragma is 3.7.17 and mapping database
files into a 32-bit address space competes with tiles and JIT.

`synchronous=NORMAL` under WAL is a recency trade, not an integrity one: WAL frames carry
per-frame checksums so recovery discards a torn tail, and the database cannot be
corrupted, only rewound. It risks transactions committed in the seconds before an abrupt
power loss. It does **not** risk anything on jetsam, which is how this process actually
dies — committed pages are already in the kernel's buffer cache. Against that, FULL costs
an fsync per commit on 2012 flash on `StorageThread`, a single serial thread shared by
every origin, and the Web thread hard-waits on it in `blockUntilImportComplete()`.

### Also established

- `SQLiteDatabase::useFastMalloc()` has no caller in this build — its only user is the
  network process, which is not built. So the `fastMallocSize`/`fastMallocGoodSize` repair
  made elsewhere does **not** reach SQLite here. Calling it would also pass
  `SQLITE_CONFIG_LOOKASIDE, 0, 0`, disabling SQLite's own small-allocation fast path.
- A `document.cookie` read costs two `URL::createNSURL()` conversions, a jar walk with
  path matching and a sort, then two UTF-16 conversions per cookie and a `StringBuilder`
  join — roughly 40 message sends and 30 allocations for ~15 cookies, rebuilt from
  scratch every read. **Not cached, deliberately:** Set-Cookie from network responses does
  not pass through `CookieJar`, and the only invalidation hook,
  `CookieStorageObserver`, has no caller in this build. A cache that misses one Set-Cookie
  serves a stale jar immediately after login.
- `StorageAreaSync` flushes on a 1 s one-shot timer, 100 items per round, so 1000 dirty
  keys take at least 10 s to reach disk — and the app calls neither `syncLocalStorage` nor
  `closeLocalStorage` on background or terminate. Now that writes actually land, that
  window is real and unowned.

## localStorage now persists — and the diagnosis took two corrections

The `sqlite3_bind_blob64` stub was real: with it fixed, every insert in
`StorageAreaSync::sync()` returns `SQLITE_DONE` where it previously returned
`SQLITE_CONSTRAINT`.

But the first attempt to verify the fix looked like a failure, because the files being
inspected were the wrong ones. `Threads-Native.app` is built from `app/native-main.m` plus
`app/native-ui.m`, and **neither calls `_setLocalStorageDatabasePath:`** — only
`app/main.m` does, and that builds a different application. So the native build falls back
to the `WebKitLocalStorageDatabasePathPreferenceKey` user default, which resolves to
`/var/mobile/Library/Caches`. The files under
`WebKitStorage/space.kern0x1b.webapp.threads/` are leftovers from the other build, last
touched 25-27 August, which is why they held the right schema and zero rows.

Demonstrated end to end on a clean database created by an uninstrumented build: write,
wait ten seconds, `killall -9` with no clean shutdown and therefore no `scheduleFinalSync`,
reinstall, relaunch — the value reads back. Pulled the database off the device: ten rows,
including the site's own `Session` key. A login now survives a relaunch.

Everything else that was suspected is not the problem, and was checked rather than
assumed: the area is persistent (`HasResourceAccess::Yes`, sync manager present, not a
transient namespace); `scheduleItemForSync` → `syncTimerFired` → `performSync` all fire on
the web thread with no broken affinity; the import completes and `blockUntilImportComplete`
never stalls; the database opens.

### A claim withdrawn

The `page_size` 1024 → 4096 pragma was reported as removing a 4x read amplification. It
does not. Two databases created on 30 August, before the change, already report
`page_size=4096` in their headers — Apple's SQLite 3.7.13 on iOS 6 ships a 4096-byte
default rather than the upstream-for-that-era 1024. The pragma is kept because it pins the
value instead of depending on a vendor default, but it is not a gain. The database header
also settles the version question empirically: `last written using SQLite version 3007013`.

### Still open

The store lives in `Library/Caches`, which the system may delete under disk pressure — a
login can vanish with no crash and no message. It is also shared with other origins
(`https_claude.ai_0`, `https_www.google.com_0`, `http_googleads.g.doubleclick.net_0` are in
there now). Moving it to the manifest's storage directory is two lines mirroring
`main.m`, but the path is captured when the `WebView` is constructed, and moving it
naively orphans the store that has just started working — including that session. Being
done as a deliberate change with migration.

### A prediction made, then withdrawn — and a fix that stands anyway

The producer/consumer mismatch in `ImageFrameWorkQueue` is real: `pending.takeLast()`
drains the global list newest-first while the completion handler matched

with two queued entries could strand one forever. Mid-scroll measurement found 16 of 17

with fixing the white cards, because that is not what was wrong. Worth recording as the

### The median and the tail are made of different things

Of 116.9 s of web-thread work in a 151 s window:

|---|---|
| JS garbage collection | **37.4%** |
| layout | 13.9% |

multi-second freeze the reader actually notices is grid and flex track sizing, with script
nowhere near it. Two page-*load* windows have the mirror image, 89.5% and 100% under

`MessagePort::drainOneLocalMessage` is on 38.8% of every web-thread stack, entered through
`sharedTimerFiredInternal → EventLoop::run → JSEventListener::handleEvent`. That is the
site's own message-handler path, and it is where the allocation driving the GC comes from.

## Garbage collection: 7.5× less, and why

Both memory-pressure bands were permanently true. `memoryFootprint()` returns
`resident_size` here, resident sits at 180-220 MB, and the bands are 148 and 162 MB — so
`shouldDoFullCollection()` and `shouldSweepSynchronously()` were satisfied at every
collection and `collectIfNecessaryOrDefer` clamped eden to 1 MB. **100 of 105 collections
in the baseline run were full marks**, each a 400-700 ms stop-the-world pass over 20-37 MB,
roughly once per second. Logged on device per collection: computed eden budget 19 MB,
actual firing at 1.1 MB.

`stopIfNecessarySlow` and `collectIfNecessaryOrDefer` are the same stack, not two triggers:
the latter ends in `collectAsync(); stopIfNecessary();`, and with concurrent GC off that
runs the whole collection inline on the mutator.

Fixed by separating what the two bands do, raising the critical eden clamp 1 → 8 MB with a
new tight clamp only above the hard band, gating the allocation-budget floor on the hard
band rather than on `isCritical` (it was dead twice over), and moving the hard band 162 →
245 MB. Measured, two passes each, identical driving:

| | GC ms per MB allocated | mean pause | full / eden | GC duty | interval |
|---|---|---|---|---|---|
| baseline | 250.0 / 199.3 | 504 / 412 ms | 87/2, 34/3 | 31.5% / 28.1% | 1.5 s / 1.2 s |
| fixed | **31.4 / 28.2** | **232 / 208 ms** | 3/6, 4/7 | **7.3% / 5.3%** | 2.0 s / 2.2 s |

No memory regression in these windows. The baseline duty cycle of 31.5% agrees with the
profile's independently measured 37.4%, which is the cross-check that both instruments are
measuring the same thing.

### A 32-bit overflow puts every armv7 build in Aggressive heap mode

`Options::aggressiveHeapThresholdInMB() * MB` is `16384 * 1048576`, which overflows 32-bit
`size_t` to 0, so `ramSize >= 0` in `growthMode()` (`Heap.cpp:242`) is always true.
Confirmed numerically rather than by reading: the observed max/heap ratio of 1.406 is
exactly `3*exp(-2)+1`, the Aggressive exponential, not the port's own 1.05 large-heap
factor. **So all the `WEBKIT_IOS6` band work in `proportionalHeapSize` is dead code on this
device.**

Deliberately not fixed. Aggressive mode also enables `maxEdenSizeForRateLimiting`
(8 × 1.92 MB = 15.4 MB), which currently suppresses collections and is load-bearing;
removing the overflow silently turns that valve off. Fix both together, with a measurement,
or neither.

## Memory: a ramp to a plateau, not a leak

Resident rises from ~90 MB to a 210-230 MB plateau inside the first 100 seconds and then
stays there — the "222 in the first quarter → 234 in the last" reading was that launch ramp
averaged into quarter one of a fifteen-minute window. Two independent confirmations: the
site **virtualises its feed** (1695 nodes and 10 articles at 17520 px of scroll depth), and
`malloc tiny` — the DOM, render tree and style — froze at exactly 44.4 MB from t=160 s and
never moved again.

### Two more corrections to the record

- **The "87 MB of large malloc blocks" is mostly the JavaScript heap.** With bmalloc
  compiled out, `fastAlignedMalloc` becomes `posix_memalign(16 KB, 16 KB)` per
  `MarkedBlock`, and libmalloc services 16 KB-aligned requests from its *large* allocator,
  one VM region each: 2577 regions × 16 KB = 41 MB against a 40.3 MB heap. No separate
  pool, no meaningful overhead. The app's live-malloc probe never saw it because it
  interposes `malloc`/`calloc`/`realloc`/`free`, not `posix_memalign`.
- **`fastMallocStatistics()` on Darwin returns `getrusage().ru_maxrss`.** Any "fastMalloc
  N MB" line in the engine's report is peak resident, not a fastMalloc figure.

The app's own region walk was also mis-attributing memory: IOKit graphics surfaces carry an
external pager, so ~55 MB of graphics memory was being reported as "frameworks", and the VM
tag table was off by one in three places (20 is `MACH_MSG` not IOKit, 63 is
`JAVASCRIPT_CORE` not sqlite, 64 is the JIT allocator not the JS heap). Fixed; the
frameworks term is flat at 138.7 MB and the graphics term is the one that moves, 2.6 → 55 MB
in sixty seconds.

### The one late crash is not a memory kill

`/tmp/native-death.log` holds 15 terminations: 12 in the first 0-3 seconds at 21-51 MB
(startup faults), one SIGTERM, and one late death at 276.7 MB after 1959 s. That one is
**SIGTRAP raised inside `free()`** on a JSC/JIT thread — libmalloc trapping on a bad
pointer. Jetsam sends SIGKILL and never reaches a handler, so a memory kill cannot appear
in this log at all. Given the port's several reference-count elisions, heap corruption is
the better reading and 276.7 MB is a bystander. Do not cite that crash as evidence that
memory drift kills the process.

### The tile layer pool was off, permanently

`LegacyTileLayerPool` initialises `m_capacity` to 0, and `canReuseLayerWithSize` begins
`m_capacity && …` — so every returned layer was refused **before** reaching the careful
memory-pressure logic added under `WEBKIT_IOS6`, which was therefore unreachable. Capacity
is only ever assigned by the `DocumentBrowser` and `PrimaryWebBrowser` cache models
(`WebView.mm:8864, 8915`), and the app pins `automaticallyDetectsCacheModel = NO`, leaving
it on `DocumentViewer` where it is never set; `setCapacity` only ever raises. So every
scroll step destroyed a tile layer and allocated a fresh 640×640×4 backing store for the
kernel to zero — the churn behind the graphics pool going 2.6 → 55 MB in a minute.

Given a real default (12 MB, `WEBKIT_IOS6_TILE_LAYER_POOL_MB`) so the existing
pressure logic — which caps the pool at 4 MB under pressure — can finally run.

### Two harness fixes that came out of getting it wrong

`scripts/measure-native.sh` runs the whole measurement as one command — launch, settle,
probe, scroll, probe, stalls, frame rate, resident, screenshot. Its first version reported
**zero stalls and no frame-rate windows on a run that had plenty of both**, because the
probe files are read once at startup and it created them before the scroll rather than
before the launch. That is the fourth harness error of the day and the reason the script
exists at all.

### The message path cost two event-loop turns per message

`MessagePort::postMessage` queued a task whose only job was to queue the delivery task, and
a task queued during `EventLoop::run` lands in the *next* generation — so one message cost
two shared-timer fires, two web-thread run-loop turns and two microtask checkpoints before
any listener saw it. The messages are same-thread: a page posting to itself through a
`MessageChannel`, which is React's scheduler yielding to the browser
(`port.postMessage(null)` from `performWorkUntilDeadline`). So the site's entire work loop
paid one wasted run-loop turn per slice — and each turn is another chance for UIKit to take
the web lock in between.

Nothing was batched, deliberately: only one message is ever in flight, and
`EventLoop::run` runs a microtask checkpoint after every task, so merging two deliveries
would let a promise resolved by handler N run after handler N+1 instead of before it.

### Threads and locks

`ParkingLot` computed `hash % size` on every park and unpark — a call to
`__aeabi_uidivmod`, since Cortex-A9 has no hardware divide — and the bucket lock spun
**forty times calling `Thread::yield()`**, which on Darwin is a mach trap that also
*depresses the caller's priority*. A contended dispatch therefore paid two software
divisions and up to eighty priority-depressing traps, all of which a profiler attributes to
`ParkingLot`. Now a mask and a sixteen-step spin with a real yield every eighth, matching
the policy already used for `WTF::Lock`.

`RunLoop` also freed and re-allocated its queue buffer every cycle, one of those frees
under the queue lock, and `WorkQueueCocoa` boxed each callable twice.

### Delegate round trips: what they were really worth

404-427 synchronous web→main handshakes per load, 1107-1724 ms of web thread parked.
Deferring the void-returning resource notifications took that to 274-283 and 853-1053 ms.

**The important part is the regression that came with it.** The first version, without a
yield, took main-thread stalls from a 0-12 baseline to 29-30 per soak. The round trip was
not only a message — it was an **unconditional web-lock hand-off**, and removing 103 of
them per load starved the main thread. Adding `WebThreadYieldIfAsked()` at the queueing
point, which hands the lock over only when the main thread has actually asked, restored the
baseline. Anyone redoing this work needs to know the hand-off, not the message, is what
those trips were buying.

Two premises handed to that agent were both wrong and it measured rather than assuming:
`_WebSafeForwarder` is fifteen forwards per session, not the hot path, and only two of 427
selectors are unimplemented, so the `respondsToSelector`-before-handshake idea is correct
and worth about one millisecond here.

## The fifteen-minute soak, and a stability regression found and fixed

The short runs above were flattered by their length. A like-for-like soak — 32 rounds of
ten 400 px flicks, the same shape as the original — gives the honest picture:

| | before waves 4-6 | hard band 245 MB | hard band 180 MB |
|---|---|---|---|
| median fps | 9.5 | 11.8 | **12.6** |
| p10 fps | 1.6 | 4.2 | 3.4 |
| min fps | 0.2 | 1.3 | 0.8 |
| frame-rate windows | 20 | 20 | 54 |
| outcome | survived | **died twice** | **survived** |

**The build crashed, and today's own work caused it.** Two SIGSEGVs at address `0x3c` —
a null pointer dereferenced at a field offset — inside `IMGSGX543GLDriver` under a
QuartzCore commit, on a libdispatch worker, at 236.5 MB after 168 s and 242.9 MB after
371 s. Identical stacks. Neither appears anywhere earlier in `/tmp/native-death.log`: every
other signal-11 entry in it is a startup fault at 21-23 MB. So this is new.

The obvious suspects were the tile changes — the coverage rect went from one half-screen to
four today, and the layer pool was given a real capacity for the first time — and
`LegacyTileGrid.mm` carries a standing warning that this exact tile count "took the process
down four times in nine soaks, twice inside the GPU driver". **They are not the cause.** A
soak with `WEBKIT_IOS6_TILE_COVERAGE_HALVES=1` and `WEBKIT_IOS6_TILE_LAYER_POOL_MB=0`, i.e.
both back to their old behaviour, died again at 371 s with the same stack.

The cause is the garbage collector's hard memory band, raised from 162 MB to 245 MB earlier
today to stop every collection being a full stop-the-world mark. That band is what keeps
resident below the point where the graphics driver cannot get a surface and dereferences
the null it gets back. At 245 the process reaches 236-243 MB and dies there.

At **180 MB** the same soak runs the full fifteen minutes with no deaths, and the frame rate
is *better* than at 245 — median 12.6 against 11.8, on nearly three times as many windows.
So the ceiling costs nothing and buys the process its life. Default changed to 180 in
`Heap.cpp` with the evidence in the comment; `JSC_IOS6_GC_HARD_MB` still moves it.

Two lessons worth keeping. A win measured over seven minutes said 245 was free; the failure
it caused takes about three minutes to appear and only in a soak, so **any memory-threshold
change needs a fifteen-minute run before it is believed**. And the first suspect was wrong:
the tile settings were new, adjacent to the failing subsystem, and carried a written warning
that named the exact symptom — and they were still innocent. The control experiment cost one
soak and would have cost a day of bisecting had it been skipped.

## WebCore is built -Oz, and that changes what "abstraction" costs here

The single most useful structural fact found in the style-value pass, and it generalises
well beyond that pass: `Source/WebCore/CMakeLists.txt:3264` compiles WebCore with **-Oz**.
At that level clang inlines almost nothing, so every layer of the modern generic value
machinery becomes a real call. Verified against the shipped binary with `nm`/`otool`, not
inferred: `ComputedStyleBase::usedZoomForLength` is out of line at 42 bytes,
`PrimitiveNumeric<…>::evaluationKind` has one out-of-line copy per range, there are 23
copies of `PrimitiveData::(minimum)ValueForPrimitiveDataWithLazyMaximum`, and **103
separate `EvaluationInvoker<Result>::operator()` forwarding thunks that do no work at all**.

`RenderBoxModelObject::borderTop()` — one edge, one box, one layout pass — is five to six
calls and three to five dependent pointer loads, ending in a `floorf` libm call, to produce
a number that is zero on almost every box on this page.

So on this port a zero-cost abstraction is not zero-cost, and the fix is usually
`ALWAYS_INLINE` on the thunks plus a fast path for the overwhelmingly common value, not a
restructuring. Note the counterweight, which is also this project's own measurement: -Oz
beats -O3 here, and inlining a 0x38-byte double-precision clamp into ~200 call sites would
be roughly 12 KB against a 32 KB L1 instruction cache. The style agent declined exactly
that for exactly that reason, and it was right to.

`usedZoomForLength` deserves its own note: everything it reads is computed at style-build
time and a style object is immutable during layout, so **it cannot change within a layout**,
and on a page with no CSS `zoom` and no page zoom the answer is 1.0 for every element. It
is now an in-object bitfield test at the call site.

## Event loop: a second wasted turn per work slice

`EventLoop::run` clears `isScheduledToRun` at entry, so the first microtask a task queues
re-arms the zero-second timer. The checkpoint then drains that microtask — and nobody
disarms the timer. Every turn that ends up containing only microtasks therefore buys a
whole extra turn: a timer reprogram, a run-loop wake, an entry into `run`, a checkpoint and
an idle-callback walk. With the message-path fix (two turns per message down to one) that
is the second wasted turn removed from every slice of the site's work loop.

The microtask checkpoint also ran **twice per message task**, the second time in the
expensive form that takes and releases the VM's API lock.

**The obvious fix here would have been wrong**, and it is worth recording why. An
early-out on an empty microtask queue skips step 4 of the checkpoint, which is the rejected-
promise notification — and that is reachable *with* an empty queue, because rejecting a
promise that has no reactions queues no microtask at all. A bare empty-queue check could
leave `unhandledrejection` unfired indefinitely. The condition used instead is the exact one
`processQueueSoon()` tests first.

## Grids: the cost is the predicates, not the algorithm

`RenderGrid::isSubgrid(direction)` is called dozens of times per item per layout, and it ran
`establishesIndependentFormattingContextIgnoringDisplayType` — `element()`, `usedContain()`,
`containerType()`, a containment check, `blockStepSize()`, five rare-data walks — **before**
testing the `subgrid` bit, which is false for every grid on this page. `isMasonry` walked to
rare grid data before checking whether the parent is even a grid. Both reordered.

Six of the eight accounted-for heap allocations per grid layout are gone: the two sizing
strategies are stateless and are now built once per algorithm rather than per run, and
`GridTrack` objects are retired into a small pool instead of being freed and re-allocated.

`RenderBox::containingBlockLogicalWidthForContent` called `containingBlock()`
unconditionally and then discarded it in the grid-item branch, where it survived only in an
assertion. `RenderObject::containingBlock` was a named hot leaf in the profile.

### The flex memo: why it was not touched, so the next attempt starts here

`FlexFormattingContext.cpp:115` resets `hasDefiniteHeight` inside the per-item loop, turning
a once-per-container percentage-height computation into once-per-item. Three specific
blockers, all established rather than guessed:

- The two writers of that memo apply **different** conditions.
  `RenderFlexibleBox::canComputePercentageFlexBasis` stores only when writing modes match;
  `FlexFormattingContext::crossSizeIsDefinite` stores unconditionally. For an orthogonal
  item `computePercentageLogicalHeight` resolves in the *item's* block direction and so
  reports the container's **inline**-size definiteness. The per-item reset is what stops
  that wrong-axis answer reaching the next item.
- The memo's inputs are not invariant over the loop: it depends on the container's
  overriding height, and `ensureBlockAxisContentSizeForFlexItemIfNeeded` lays an item out
  mid-loop, which re-enters for nested flex.
- `computePercentageLogicalHeight` has a side effect — `addPercentHeightDescendant` — so a
  hoist changes how many times that runs, not only how many times a value is computed.

Also worth knowing for triage: the memo is only consulted on the expensive path for
**column-flow** containers or percent/stretch cross sizes, so for a plain row-flow card the
reset is already free and the 67.9% inclusive figure for `FlexFormattingContext::layout` is
item layout, not this.

## The JavaScript realm: right target, wrong numbers, and the proposed fix rejected

Corrections to what was handed over: a realm is **1.95 KB** on 32-bit, not 2.5-3 KB; it
installs about **161** eager `JSFunction` cells, not a thousand; `StringPrototype` is 37
installs, not 48; and `MathObject`, the fattest single file at 37, is **already lazy**.
`NativeExecutable` is cached VM-wide, so a second realm pays only for cells.

Realms are created **2-6 per cold load and rebuilt on every cross-document navigation** —
`JSWindowProxy::setWindow` has no reuse path, the only skip is a pointer-identity check, and
origin plays no part. With the back/forward cache at zero, Back is a full re-navigation too.
So creation cost recurs; SPA route changes cost nothing.

**The static-property-table direction was rejected**, with three mechanisms. Reification
transitions the prototype's structure one property at a time, and each transition fires the
structure's transition watchpoints, invalidating every inline cache and every DFG
`ObjectPropertyCondition` recorded against that prototype — up to 37 invalidation waves
spread across a page load, on a build where prototype caching only began working today.
`reifyAllStaticProperties` converts the object to a dictionary, which poisons prototype-chain
caching, and feature-detection code does enumerate builtin prototypes. And a static table
taxes every put that walks that prototype. Intrinsics survive reification, so they are not
the blocker; the inline-cache timeline is.

The agent also downweighted its own marking argument: generational GC means realm cells are
re-marked only on full collections, and 161 cells is about 1% of a 20 MB heap's object
count. The recurring cost that matters is creation, not marking.

Two conversions were taken — three `Symbol.species` getter/setters and
`AsyncFromSyncIterator` — and the eager iterator structures were left alone because
`DFGByteCodeParser` reads them on the **concurrent compiler thread**, where
`LazyProperty::get` asserts. `BigInt` is blocked harder still: `InlineCacheCompiler` emits a
JIT load of `m_bigIntPrototype` at a fixed offset.

## The collector was judging itself by the shared cache

`WTF::memoryFootprint()` returns `resident_size` on this port, and the comment justifying it
is correct as far as it goes: `TASK_VM_INFO` answers at revision 0 here so `phys_footprint`
is noise, and resident size is what jetsam judges a process by.

But `resident_size` counts **every** resident page the task maps, including the shared cache
and our own framework text. The memory investigation measured that term separately:
**138.7 MB, flat, of a roughly 220 MB total.** So the number the collector uses to decide
how hard to collect is dominated by system libraries, and it crosses the 180 MB line when
more of the shared cache is paged in — not when anything the collector can influence has
grown. Collecting harder does not unmap libobjc.

That is the mechanism behind the profile's headline: below 180 MB the collector spends 5.4%
of wall clock at an 83 ms mean pause; above it, 34.2% at 410 ms with every collection a full
mark. The crossing happens 21 seconds in, before the feed has finished loading, and the
process never comes back.

**Revision 0 does carry `internal`** — the task's own anonymous memory, which is what
`phys_footprint` approximates upstream. The SDK header puts `internal`/`external` well
before `phys_footprint`, and `TASK_VM_INFO_REV0_COUNT` is defined as "doesn't include
phys_footprint", so it is available on this kernel. `memoryFootprint()` now returns
`internal + compressed`, with `WEBKIT_IOS6_FOOTPRINT=resident` restoring the old number for
A/B.

Two things to keep straight, because they are different questions that were being answered
with one number:

- **How hard to collect** is about memory the collector can influence — anonymous, dirty.
- **How close the process is to being killed** is about `resident_size`, because that is
  what jetsam reads. The application's own valves in `native-ui.m` should keep using it.

Not yet measured on the device — the phone was in use by another agent when this landed.
The number to look for is the reported footprint dropping from ~220 MB to something near
80 MB, and the collector staying in its cheap band for the whole session.

## Startup is not the problem, and three assumptions died with it

Measured with `kinfo_proc.p_starttime` (`DYLD_PRINT_STATISTICS` does not exist in this
2013 dyld): **process start to the first page byte is ~1.25 s of a 20-28 s launch, about
5%.** The remaining 19-27 s is network and the site's own JavaScript.

- **Static initialisers: five, across every image we ship, twenty bytes total.** WebKit uses
  function-local lazy statics throughout. Nothing to win; closed.
- **Mapping all three large frameworks costs about 8 ms**, because Mach-O text is
  demand-paged. **73.4 MB of shipped image text costs about 6 MB resident.**
- **The 32 MB JIT reservation is address space, not memory** — `tryReserve(commit=false)`
  plus `MADV_FREE_REUSABLE`, committed a page at a time as code is emitted. 342.6 MB mapped
  against 6.1 MB resident right after `dlopen` proves it, and `memoryFootprint()` does not
  count it. Shrinking it buys nothing and caps JIT code.

So the "~100 MB of fixed cost before a page byte" I handed that agent was wrong: resident at
the first page request is **22.3 MB**. The 99 MB logged at the first collection is already
about 77 MB of site content.

**Unreachable subsystems, measured `__text`: 1.13 MB, 3.5% of 31.8 MB.** The whole list —
inspector agents, content extensions, Web Audio, service workers, accessibility, text
tracks, WebSQL, IndexedDB, WebGL residue, back/forward cache, plugins, geolocation, speech,
notifications — adds up to less than the noise, and their resident cost is near zero. That
independently confirms the recorded dead end (25 features off gave 254 KB and a black page).
There is no megabyte of headroom under any memory line to be had by deleting dead engine
code.

Three larger items that are not feature-shaped: ICU's data table is 22.0 MB but lives in
`__TEXT,__const`, is never rebased and never dirtied, so it costs nothing at startup or in
residency; the generated DOM bindings are 2.01 MB of text and 0.28 MB of `__DATA,__const`,
the latter being what WebCore's **51,757 eager bind fixups** write into, 46,013 of them into
JavaScriptCore over only 662 distinct symbols; and `WTF::Logger` is 230.8 KB across 1,116
call sites whose `willLog()` builds a `Vector<JSONLogValue>` with a string conversion of
every argument *before* testing `m_enabled` — all but about thirty of those sites are in
media code, so it is a size cost rather than a speed one.

Inside the 471 ms of `WebView` construction, the one clean win found and handed on rather
than taken: `counterStyles.css` is 19,060 bytes and 94 `@counter-style` rules parsed
eagerly, 17.8 ms, and a second `html.css` rule set is built for printing that a UIWebView
app never uses.

## Concurrent garbage collection: a definite no, and the guard is load-bearing

`Options::useConcurrentGC()` is forced false for anything that is not x86-64 or arm64. That
looks like a blanket platform exclusion made without measurement, and turning it on would be
worth up to 15.08 s of a 38.8 s busy scroll, since 88.9% of GC samples are the mutator
running the collector itself while the second core sits idle.

**It cannot be turned on.** That guard is what makes the C++ heap writers correct. Roughly
forty places write live cell-bearing slots with a bare two-word store, outside the publish
protocol — `JSArrayInlines.h:82` (`pushInline`, the hottest one for a feed),
`JSObject.h:491` (`putDirect`'s fast path), the indexing-type conversion loops in
`JSObjectInlines.h`, Map/Set entries, `ScopedArguments`, global slot growth,
`ArrayPrototype::concat`, plus raw `memmove` in `ButterflyInlines.h` and `JSArray.cpp`.
`JSValue::decodeConcurrent` detects tearing only by seeing `InvalidTag`, and these writers
never publish one.

The generated code is fine — all thirteen LLInt publish sites are covered and both JITs
route through `storeValue`/`storeCell`. Two candidates were checked and **cleared**, so
nobody chases them: the Int32Shape contiguous store in `LowLevelInterpreter32_64.asm:1879`
and `compileArrayPop`'s empty-tag write can only ever produce non-cell combinations, which
the collector discards.

One coupling worth knowing: the JIT-side publish protocol is gated on
`Options::useConcurrentJIT()` (`AssemblyHelpers.h:88`), not on concurrent GC. So concurrent
GC correctness would silently depend on an unrelated option staying true, with no assertion
tying them together — and turning concurrent JIT off is a plausible experiment on this
device.

## One constant, four symptoms — and I set it

`shouldDeleteAllCodeForMemoryPressure()` in `page/MemoryRelease.cpp` compares its own
`residentMegabytes()` — a separate `TASK_BASIC_INFO` read, not the collector's
`memoryFootprint()` — against a threshold I lowered from 235 MB to **160 MB** this morning.
The process runs at **204-236 MB resident**. The test is therefore **always true**, and every
firing of the application's memory valve throws away every compiled function.

Measured: **compiled code was fully discarded twice in a 157-second run**, at t+86 s and
t+151 s. Peak tier state before a wipe: 502 LLInt blocks, 1116 baseline, 531 DFG.

The morning's reasoning was that 235 MB was above every valid measurement and so the
threshold was dead, which was true of the numbers *then*. The process has grown since, and I
did not re-derive it. That is precisely the rule this file already records after the same
mistake was made once today — "thresholds tied to resident memory must be re-checked after
any change that moves the size of the process, or they silently become always or never" —
and I broke it the same day I wrote it down.

**Four separate findings collapse into this one cause:**

- **28,456 condition-set allocations in 100 s (280/s), 68% of all C++ allocation on the web
  thread.** Inline caches are not thrashing on their own merits; they are being deleted with
  the code and rebuilt from nothing, twice a run.
- **The tier-up conclusion that everyone has been forbidden to re-litigate.** Its stated
  reason — "paying baseline compilation for the thousands of functions a bundle calls once
  costs more than the interpreter does" — is now measured false on both halves: the entire
  baseline leg costs **+2.9 MB of a 27.2 MB pool** at 16.3 bytes of machine code per
  bytecode word, and the live interpreted population is not call-once functions, with only
  **5 blocks below 15 executions against 211 sitting between 200 and 499** — 40% of the way
  to a threshold of 1000 and never arriving. What the old experiment actually measured was:
  compile sooner → more memory → the valve fires more → all code deleted → more
  recompilation. The threshold was never the lever.
- **`CodeBlock::~CodeBlock` sets `didOptimize = False`** when a baseline block dies before
  reaching the DFG, and `UnlinkedCodeBlock::thresholdForJIT` then **quadruples that
  function's next threshold**, to 2000. So each wipe does not merely cost a recompilation —
  it ratchets the whole session toward the interpreter.
- **Two lock findings that only bite under recompilation.** `valueProfileLock()` is
  `NoLockingNecessary` on 64-bit and a **real `CodeBlock::m_lock`** on 32-bit, taken by the
  mutator on every JIT/OSR threshold tick and held across every value profile in the block,
  while the DFG thread takes the same lock — a lock that does not exist on any build upstream
  has ever tuned. And `FixedVMPoolExecutableAllocator` has **one process-wide lock** taken on
  every `LinkBuffer::allocate`, acquired *while* the CodeBlock lock is held, so a slow
  allocation on the −8-priority compiler thread extends the mutator's hold.

The experiment that settles it is one environment variable and no rebuild:
`WEBKIT_IOS6_CODE_DELETION_THRESHOLD_MB=250`, above the operating range, so deletion never
fires. If the frame rate responds, the lever was never `thresholdForJITAfterWarmUp` — it was
this constant.

### Also eliminated, so nobody spends a run on them

`StructureRareData` and `WatchpointSet` have no locks at all; watchpoint firing is lock-free
atomics. The JS-heap allocator locks cannot be two-thread contended with concurrent GC off —
the only non-mutator toucher runs while the world is stopped. And `JSLock`/`VM::m_apiLock` is
**uncontended**: there is one JS thread, neither the DFG thread nor the GC helper acquires
it, and it is taken per DOM→JS entry rather than per event-loop turn or per microtask
checkpoint. Its cost is bookkeeping, not waiting.

One caveat that does apply: because this build uses the system allocator, the DFG thread's
graph allocations and the mutator's allocations **do** contend — on libmalloc's zone locks,
which are not `WTF::Lock` and are therefore invisible to any instrument that counts those.

### A measurement correction that affects every frame-rate number in this file

The frame-rate distribution is **bimodal**: an idle window sits at 60 and a scrolling window
in single digits, so a median over all windows mostly reports how much of the run was idle.
`scripts/measure-native.sh` now separates them and reports the scrolling windows only.
Recomputed on that basis, the soak comparison that read "median 18.8 against 12.6" is not
supportable — the surviving configuration logged only 13 scrolling windows against 85, which
is too few to compare. What stands without qualification is the stall count, which is
event-driven rather than sampled: **236 before this work, 19 after.**

## A deterministic bench, and the baseline it establishes

The live site cannot answer "is this build faster". Its content varies per load, resident
memory tracks that content at r = 0.98 (8.6 MB per thousand elements), and it rate-limits.
The consequences were not subtle: **the same engine configuration measured 29, 107 and 122
stalls across three soaks**, and three runs that reached an identical JIT state scrolled at
15.5, 7.0 and 8.0 fps. Every threshold conclusion drawn against it — including several hours
of my own work — was measuring noise.

`tests/scrollbench.html` plus `scripts/bench-native.sh` replace it for engine comparisons.
The page builds 400 posts from a seeded sequence, so the DOM is identical between runs; it
carries the shape the profile actually found on threads.com (hundreds of small per-card
grids, 48px/248px tracks, text-dominant) rather than an invented one; and it runs a
`MessageChannel` self-post loop, which is what React's scheduler does and what put
`MessagePort::drainOneLocalMessage` on 44.1% of every web-thread stack. Frames are reported
as the distribution of gaps between animation callbacks, not as a mean — on this device a
mean is dominated by whichever windows were idle.

Three consecutive runs, same build:

| | a | b | c |
|---|---|---|---|
| elements | 3710 | 3710 | 3710 |
| scrollHeight | 75837 | 75837 | 75837 |
| frames | 1563 | 1561 | 1576 |
| gap median | 34 ms | 34 ms | 33 ms |
| gap p90 | 37 ms | 37 ms | 37 ms |
| gap p99 | 112 ms | 96 ms | 86 ms |
| gap max | 269 ms | 259 ms | 263 ms |
| over 100 ms | 17 | 12 | 12 |
| over 400 ms | 0 | 0 | 0 |
| stalls | 3 | 1 | 2 |
| build | 3710 ms (cold cache) | 1581 ms | 1585 ms |

Median and p90 reproduce to a millisecond; only the tail moves. A cycle is four minutes
instead of fifteen, and it cannot be poisoned by the site refusing to serve.

**What it does not measure, stated plainly:** 34 ms per gap is 29 fps, against 5-15 fps on
the real site. The difference is the site's own JavaScript, which is far heavier than this
imitation. So the bench measures the engine, not the product. It is the right instrument for
"did this change help the engine" and the wrong one for "is it usable now" — the live soak
stays for acceptance, but rarely, and never as the thing a decision hangs on.

Two guards are built into the driver because both mistakes have already been made here: a
run whose flick never fired is discarded rather than reported (an idle app once produced "one
stall instead of 236", which I nearly reported as a result), and a run where the page did not
load is discarded rather than averaged in as a fast one.

### Also recorded: the thresholds are back where they started

`memoryFootprint()` was changed to return the task's own anonymous memory instead of
resident size, on the reasoning that resident counts 138.7 MB of shared cache and framework
text that neither collecting nor discarding code can release. **The change did nothing** —
logged side by side, footprint equalled resident to the megabyte on every call (228/228,
224/224, 229/229, 233/233), so either `TASK_VM_INFO` is refused at this revision and the
fallback runs, or the two are the same quantity here. The collector's bands and the
code-deletion gate were then recalibrated onto a scale they were already on, and the soak
that followed died twice and wiped code seven times.

All of it is reverted: bands 148/180, deletion gate 235 on resident, application valve
148/162. The own-memory path is left in place but disabled, behind `WEBKIT_IOS6_FOOTPRINT=own`,
with a one-shot log of the `task_info` return code and the raw fields — which is what should
have been checked before anything was built on it.
