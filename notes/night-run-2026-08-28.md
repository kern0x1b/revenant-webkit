# Ночной автономный прогон, 2026-08-28

Правило цикла: замер → одно изменение → 15–20-минутный прогон на устройстве →
оставить или откатить по числам. Прогон: анимированные флики UIKit + переходы
по ссылкам + возвраты, автоперезапуск после смерти, каждый трейс сохраняется.

Метрика прогона: раундов всего / смертей (все смерти до сих пор — SIGKILL по
памяти, порог ~175–182 МБ резидентно).

## База на начало ночи
- soak4 (клапан памяти): 88 раундов / 1 смерть — лучший результат.
- soak5 (LTO-JSC): 49/3 — откачен, JSC остаётся обычным.
- -Oz WebCore: __TEXT 39.7 → 23.5 МБ (−41%); relayout живой ленты 42 мс.
- Выключены навсегда (физически невозможны на iOS 6): MODEL_ELEMENT,
  PICTURE_IN_PICTURE_API, AVF_CAPTIONS, REMOTE_INSPECTOR (его инициализация
  давала первое же замирание UI на старте), CONTENT_FILTERING (падал),
  WK_WEB_EXTENSIONS. WIRELESS_PLAYBACK_TARGET возвращён: его флаг гейтит
  SPI-заголовки PAL, без него не собирается, рантайм за soft-link-гардом.

## Открытые дефекты (очередь)
1. Возврат позиции после баннера не срабатывает (restores: 0).
2. Смерти по памяти на первой гидрации (клапан реагирует не раньше опроса тайлов).
3. Ввод текста пальцем не подтверждён (синтетический путь не поднимает клавиатуру).
4. Логин-флоу не пройден целиком.
5. Строки JS: rope+slice ~1.6× медленнее движка 2012 (вторично).

## The two frames per second: found, and it was ours

The user's report never matched my own numbers, because I had been measuring the
wrong thing. My frame-rate probe ran through `requestAnimationFrame`, which
lives on the web thread and happily reported sixty while the screen visibly
stuttered. The interface is composited on the main thread, so that is the only
place a frame counter means anything. A `CADisplayLink` on the main run loop
(`startCountingFrames` in `app/native-ui.m`) reproduced the complaint on the
first try: idle 60, and 9.5 then **0.9** frames per second during a flick.

The watchdog already photographed the stalled main thread, and every sample sat
in `_WebThreadLock`. A stack of a waiter says nothing about the holder, so the
watchdog now also names and photographs the web thread whenever the main
thread's stack mentions the lock (`findWebThread`, `stackMentionsWebThreadLock`).

Four of seven holder samples were in `JSC::BytecodeGenerator` — the engine was
compiling the site's JavaScript to bytecode, over and over, while holding the
web lock, during scrolling. One more was rebuilding the system font cascade
list.

The cause was my own memory valve. `+[WebView _releaseMemoryNow]` is
`releaseMemory(Critical::Yes, Synchronous::Yes)`, and `releaseCriticalMemory()`
ends in `GarbageCollectionController::deleteAllCode()`. It also drains the CSS
value pool, empties the font caches and releases the style resolver. I had that
firing every eight seconds above 138 MB resident, and a second copy of the same
call in `LegacyTileCache` on a ten second timer. Resident sat at 130–150 MB
routinely, so the engine spent the whole session throwing away every compiled
script and rebuilding it under the lock — and the rebuild allocates, which
pushed resident back up, which fired the valve again.

Both valves are now graded. Routine pressure gets a collection and the cheap
caches (`Critical::No`, via a new `+[WebView _relieveMemoryPressure]`); the
destructive level waits for 162 MB resident or system memory level under ten,
rate-limited to once a minute.

Measured after, on a 6.5 minute continuous-flick soak:

| | before | after |
|---|---|---|
| worst interface frame rate under scroll | 0.9 fps | 47 fps |
| main-thread stalls over 400 ms | 7 in 40 s | 1, at startup only |
| scroll position thrown to the top | 6 events | 0 |
| resident / peak | 130–150 MB | 116 / 138 MB |
| valve activations | continuous | 0 |

The valve was not merely unnecessary at these levels, it was manufacturing the
pressure it existed to relieve.

## Fourth, fifth and sixth font bridges

An audit of every ObjC method on the WebKitLegacy iOS surface that returns a
CoreFoundation type found three more of the crash class that killed the typing
session:

- `-[DOMElement _font]` (`mac/DOM/DOM.mm`) returned a raw `CTFontRef`. It has no
  callers inside the engine at all — it exists only so the embedder can ask a
  focused element what font it is drawn in, and on iOS 6 the embedder is UIKit.
- `FontAttributes::createDictionary()` stored `bridge_cast(font->ctFont())` under
  `NSFontAttributeName`, which is the key every consumer treats as a UIFont.
  This dictionary is what `-[WebView typingAttributes]` hands back after each
  keystroke.
- `[style setTextLists:]` in the same function is an AppKit-only selector; it now
  goes through `respondsToSelector:`.

And one that is not a font at all but the same shape, sitting on a much wider
path: `WebCore::cocoaColor()` in `ColorCocoa.mm` converted every colour in the
engine by sending `_disambiguated_due_to_CIImage_colorWithCGColor:` to
`UIColor`. That spelling exists to dodge a CIImage category added years after
iOS 6; here it is simply absent, so the first colour attribute the engine
produced would have died on the class. It now falls back to
`+colorWithCGColor:`.

Also fixed: `-[WebFrame interpretationsForCurrentRoot]` dereferenced `core(self)`
with no null check, alone among its neighbours, on the dictation path.

Still unverified by machine: real keyboard input. Synthetic taps do not raise
the UIKit keyboard, so the `addInputString:` route cannot be exercised from
here; the styled-field probe (a form inside a list, italic Georgia, coloured
text, focus, submit) survives, which covers the typing-attributes and colour
paths but not the keystroke itself. The probe now removes its own elements —
the previous one was left in the page and the user saw it as a stray "ABC"
field, which also dragged the page to the top whenever it took focus.

## The measurement was fiction, and so was the injected script

Two findings that invalidate a lot of earlier work.

**The flick harness was scrolling nothing.** It animates the UIWebView's own
scroll view. While the app-install sheet is up the site collapses the document
to a single screen - `scrollHeight` 460, the scroll view's `contentSize` 460,
"reachable 0" in the harness's own log - so every frame-rate figure taken during
a "scroll" was taken on a page that could not move. The 47 frames per second I
reported was real arithmetic over an idle screen.

**`inject.js` was never on the device.** `install-native.sh` copied the
executable, `NativeUI.dylib`, `Info.plist` and the frameworks, and nothing else.
The app read the script out of its bundle, got nil, and injected nothing - for
the whole project. `window.__appchromeV` read 0 on the device. So the banner
handling, the "get the app" retargeting, all of it, has never run.

**And the sheet only closes on a full press sequence.** `element.click()` leaves
it up; `mousedown` + `mouseup` + `click` built with `document.createEvent` and
aimed at the control's centre dismisses it every time, and the document goes
from 460 to 2080. An earlier version of the script had concluded that a
page-made event was untrusted and routed the press through a native bridge - a
whole mechanism built on a wrong measurement, now deleted.

With the script shipping and the press fixed, the sheet is gone by itself before
a person sees it, and the feed is 4455 px tall and scrollable.

**The honest frame rate, measured on a feed that actually scrolls: 2.4 to 9.7
frames per second.** Which is exactly what the user has been describing from the
start. Every number in the table above was measured on a frozen page; only the
memory and stall figures there survive.

## Accelerated overflow scrolling: enabled, crashed, reverted

While the sheet is up the feed lives in a `position: fixed; overflow-y: auto`
container (`scrollHeight` 1836 against `clientHeight` 460), and this port has no
accelerated overflow scrolling at all: `ENABLE_WEBKIT_OVERFLOW_SCROLLING_CSS_PROPERTY`
was off, and `asyncOverflowScrollingEnabled` is false for WebKitLegacy, so
`canUseCompositedScrolling()` returned false unconditionally. Scrolling such a
container repaints it and runs a full compositing update every frame.

Turning the feature on and promoting every scrollable overflow area is not
survivable: `RenderLayerBacking::updateConfiguration` reaches for a scrolling
coordinator that WebKitLegacy does not have, and the process takes SIGSEGV about
forty seconds into the feed, inside a compositing update driven from
`-[LegacyTileLayer layoutSublayers]`. Reverted to opt-in via the CSS property;
the build flag stays on so a per-element opt-in is available later. With the
sheet dismissed the feed scrolls the document, not a container, so this is not
on the critical path.

## Tiles are starved during a fast scroll

From the device's own log while scrolling a 5108 px document: `[tiles] 3 tiles of
320x320 (1.6 MB each) = 4.7 MB, coverRect 320x920`. Three tiles and 920 px of
look-ahead. A flick outruns that immediately and the engine repaints ahead of the
finger for the whole gesture. The budget is being cut by our own tile-budget code
because the system memory level sits at 9-19 - and at level 9 the process was
SIGKILLed at 106 MB resident, so the pressure is the device's, not ours.

## Notes on instrumentation, learned the hard way

- Never delete a log file while the app is running: the process keeps writing to
  the unlinked inode and the new file never appears. Cost two measurement rounds.
- `triggerFired()` seeds itself on the first successful `stat`, so a trigger file
  that did not exist at launch needs two writes before it fires.
- The main-thread profile during a scroll is 83% `mach_msg_trap`: the main thread
  is idle and waiting. The work is on the web thread.

## The web thread spends the scroll in JavaScript, and the JIT was off

A stack sampler aimed at the web thread by name (`findWebThread`, 25 Hz, whole
frame-pointer chain) over eight flicks on a feed that really scrolls:

| | share of samples |
|---|---|
| JavaScript (property-access slow paths, LLInt dispatch, lexer) | 54-62% |
| layout and paint | 13-14% |
| waiting | 7-15% |

So the engine's rendering was never the problem. The site's script is.

That led to the JIT. `isJITEnabled()` requires the `dynamic-codesigning`
entitlement through `processHasEntitlement()`, which goes via
`SecTaskCreateFromSelf` and an XPC entitlement lookup - neither answers on this
system, so it reported no entitlement and `disableJIT()` ran before anything was
ever compiled. And `MAP_EXECUTABLE_FOR_JIT` is `MAP_JIT`, a flag that arrived
years after iOS 6: passing it to `mmap` fails with EINVAL, so even past the
entitlement the executable region could not be reserved. Both are now bypassed
under `WEBKIT_IOS6`, and the device confirms it:

    [jit] reservation of 33554432 bytes succeeded (useJIT 1)

Measured, three million iterations of `s += i`:

| engine | time |
|---|---|
| ours, JIT working | 53 ms (56M iterations/s) |
| the system's iOS 6 engine | 288-378 ms (10M/s) |

**Our JavaScript is 5.5 times faster than the system engine's.** Worth knowing
why the system one is slow too: UIWebView did not get the JIT on iOS 6 - only
MobileSafari carried the entitlement - so the platform everyone remembers as
"UIWebView is sluggish" was running everything interpreted.

A first benchmark using `s += (i*3)%7` showed no difference at all between the
two engines and nearly fooled me into the opposite conclusion: integer division
is slow on a Cortex-A9 whether or not the loop is compiled, so the modulo hid
the entire effect. Pick benchmark arithmetic that the hardware does quickly.

## Scroll events throttled to what this platform used to do

Publishing the on-screen rectangle every frame also fired a DOM scroll event
every frame, and a feed answers that by deciding which posts exist. Sixty of
those a second is unaffordable here, and it is not what iOS of this era did -
the scroll event did not arrive continuously during a drag at all. Now: at most
one every 250 ms while the finger moves, and one when it stops.

## Memory is the binding constraint again, and it is partly the device's

At the moment of a kill, from the process's own region accounting:

    our frameworks 20.6 MB; executable (JIT) 16.5 MB; malloc heap 61.0 MB;

the graphics figure is not coming from those layers. The relaxation is reverted
anyway, since the reason for it - fixed things painted at a stale offset - is now

## My own instrumentation was crashing the app

SIGSEGV at 0xffffffbc on a bare `thread_start` stack, no engine frames: the
sampling threads walk a suspended thread's frame-pointer chain by dereferencing
raw pointers, and a thread caught mid-prologue has whatever the last frame left
in r7. Every stack walk now goes through `vm_read_overwrite`, which returns an
error instead of faulting.

## The bars: two of my own regressions, and a platform gap

**Regression one.** Narrowing fixed-position layer promotion back to upstream
(done earlier in the session, hunting the 52 MB of graphics that turned out not
to be layers) left every fixed element painted from the render tree, which on
this port only learns the scroll offset at the next layout. That is precisely
"bars drift with the content and snap back". Restored.

**Regression two.** The viewport publisher only fired when the scroll offset
*changed*. At load the offset is zero and never changes, so the engine was never
told where the window is at all, and a bar laid out against that default landed
at the left edge and jumped down on the first scroll - exactly what the user
described. It now publishes on the first frame and on any change of rect,
position or size.

**The platform gap.** `CABackdropLayer` does not exist here, so a
`backdrop-filter` is silently dropped and the element keeps the translucent
background it declared. The bars became windows onto the page - and during a
scroll what shows through is the tile behind them, still holding the previous
frame, so the bottom bar appeared doubled and smeared. Screenshots taken mid-drag
show it plainly. `StyleAdjuster::adjust` now makes a declared translucent
background opaque whenever a backdrop filter is present and cannot be honoured:
an opaque bar is the nearest honest rendering of a blurred one. Verified by
screenshot - the bar is solid, the icons are clean, nothing bleeds through.

Note: clearing the backdrop filter itself takes SIGTRAP inside `Adjuster::adjust`
(a default-constructed `FilterValueList` is not a valid "none"), so the filter is
left in place and only the colour is adjusted.

Startup is now 13.1 s to a usable feed, from 22 s earlier today.

## The freeze was a four-line compatibility shim I wrote

`+[CATransaction addCommitHandler:forPhase:]` does not exist on iOS 6, so
`compat/ios6_missing_classes.m` supplies it. Mine hopped the PostCommit block to
the main queue.

The engine registers that handler **from the web thread**, at the end of its own
rendering update, and the block is
`-[WebView _didCompleteRenderingUpdateDisplay]`. Run on the main thread it does
two things it must not: it touches `page->didUpdateRendering()` with no web lock
at all, and it calls `schedulePostRenderingUpdate()`, which binds a **repeating**
run loop observer to whatever run loop it happens to find and never rebinds it
(`if (m_runLoopObserver) return;`). Bound to the main run loop, in the common
modes - so inside a scroll drag as well - and its body opens with
`WebThreadLock()`.

So the main thread was acquiring the web lock **on every turn of its own run
loop, for the life of the process.** Whenever the web thread was inside a script
handler, the interface was simply gone: no frames, no taps, the display link
stopped, every trigger poller stopped. That is the "buttons do nothing" the user
kept reporting, and no amount of work on the bars was ever going to touch it.

The block now goes back to the web thread, where the same observer binds to the
web run loop and its `WebThreadLock()` is a recursive no-op.

## Everything else of mine that was blocking, and is now not

An audit of every `#if defined(WEBKIT_IOS6)` guard and all of `app/` for blocking
primitives found, in order of what it cost:

- `reportReadiness` evaluated JavaScript from the main thread every two seconds
  **forever** if the feed never grew past 700 px - one guaranteed stall every two
  seconds for the whole session. It now reads the scroll view's content size,
  which takes no locks.
- The `_WebSafeForwarder` swizzle wrote a line to a file for **every delegate
  message**, with `fopen`/`fclose` each time, and the web thread executes that
  path while still holding the lock. Off unless asked for.
- The `setContentOffset:` swizzle intercepted every frame of every scroll. Off
  unless asked for.
- The stall watchdog called `dladdr` and `fprintf` **while the main thread was
  suspended** - both take locks the suspended thread may hold, so the instrument
  could wedge the process permanently while diagnosing a stall that would have
  cleared. It now captures registers and walks the stack inside the suspend
  window and does all naming after resuming.
- `writeSnapshotBurst` called `sleepForTimeInterval:0.12` three times on the main
  thread: 360 ms of deliberately blocked interface inside a diagnostic. Chained
  with `performSelector:afterDelay:` instead.
- Four `getenv("WEBKIT_IOS6_LOG_*")` calls sat in `fillRect`, in the frame paint,
  in the per-tile repaint and in font realization. Darwin's `getenv` scans the
  environment and takes a lock, and the "only log 25 times" cap was **inside** the
  check, so the cost never went away - thousands of environment scans per painted
  frame on the web thread under the lock. Read once into a `static const bool`.
- `logLine` opened and closed `/tmp/native.log` on every line, from paths that run
  per frame. Opened once.
- The composited-layer counter walked the whole render layer tree every three
  seconds, ungated, on the web thread inside the rendering update. Gated.
- `[center]`, `[tiles]` and `[tilebudget]` in the tile code logged unconditionally;
  `WTFLogAlways` reaches a file through an unbuffered stderr, so each was a
  synchronous write on the web thread, some on paths that run per scroll. All
  behind one flag now.
- The missing-class notices in `compat/` printed on **every** `+alloc`. Once each.
- `keepInjectionApplied` was dead code that would have made three main-thread JS
  evaluations periodic if anyone had ever wired it to a timer. Deleted.

## What the remaining slowness actually is

The long freezes have a name now. A reporter added to `JSC::profiledCall` - it
times every entry from the engine into script and names the callee when the call
runs long - printed this, three times in ten flicks and twice during a load with
no scrolling at all:

    3061 ms in N at https://static.cdninstagram.com/rsrc.php/v4/yO/r/Yow4V0sR0h4.js:240
    6895 ms in N at .../Yow4V0sR0h4.js:240
    2605 ms in N at .../Yow4V0sR0h4.js:240

Line 240 of that bundle is `Scheduler-profiling.classic` - React's scheduler - and
`N` is `performWorkUntilDeadline`. Its work loop is

    for (k(t), h = s(_); h !== null && !(h.expirationTime > t && P()); )

where `P()` is `shouldYieldToHost`. It yields only if the task has **not** expired.
Once a task expires React runs it to completion without yielding, and calls the
callback with `didTimeout = true`, which is the synchronous whole-tree render. On
this CPU the work expires before it finishes, so React falls off its cooperative
path into a multi-second uninterruptible render, holding the web lock.

Two hypotheses were tested and are wrong, so they should not be revisited:

- **The clocks are fine.** `performance.now()` advances (17 ms across a 200k loop),
  `Date.now()` agrees, `MessageChannel` exists. A frozen clock would have made
  `shouldYieldToHost` never fire; it isn't that.
- **The task queue is fast.** 30 `MessageChannel` round trips in 17 ms, worst hop
  4 ms; 30 `setTimeout(0)` hops in 8 ms, worst 1 ms. React's yielding is not
  being starved by our event loop.
- And JavaScriptCore is **not** in mini mode: `VM::isInMiniMode()` is
  `!Options::useJIT() || Options::forceMiniVMMode()`, and the JIT is on now. Worth
  noting it *was* in mini mode for the whole project before the JIT fix, which
  also meant unlinked code blocks were being jettisoned aggressively.

The page's own rendering update runs at about **15 Hz** (200 `requestAnimationFrame`
callbacks in 13.0 s), which is the rate at which anything the page does becomes
visible, independent of the 60 Hz the interface now holds.

## Cutting the engine down

The honest accounting finally located the memory. From the subsystems' own
counters, at 159 MB resident: the page accounted for about 40 MB (JavaScript heap
20, resources 11, decoded images 3, tiles 6) and the other 91 MB was **our own
engine binaries, mapped privately into the process**.

Worth being precise about what that means, because it changes what is worth
doing. A binary is not loaded into RAM; it is mapped, and pages fault in as code
executes. Those pages stay clean and the kernel can drop them at will. But two
things make them count here anyway: iOS 6's jetsam decides by resident size,
which includes clean mapped pages; and the system's own frameworks live in the
245 MB `dyld_shared_cache_armv7`, mapped **shared** so their pages are charged
once system-wide, while ours are private to one process.

Sizes, and what each step bought:

| | WebCore | JavaScriptCore | WebKit | total |
|---|---|---|---|---|
| as built, -O3 | 60.8 | 45.9 | 2.6 | 109.3 |
| after `strip -S -x` | 46.3 | 42.6 | 1.9 | 90.8 |
| rebuilt `-Oz`, then stripped | **27.6** | **36.3** | **1.9** | **65.8** |

For scale, iOS 6's own WebCore was around 25 MB and its JavaScriptCore around 8.
We are no longer far off on WebCore.

`-Oz` now covers every target that carries code, not just the umbrella one
(`WebCoreDOMAndRendering`, `WebCoreBindings`, `WebCoreSVG`, `WebCoreHTML`,
`WebCorePAL`), and JavaScriptCore as a whole - except `LowLevelInterpreterLib`,
which keeps `-O3`: it is the hot path for every line of script and the one place
where speed is worth its bytes. Also disabled: MathML (renders no part of a site
like this), web notifications (no delivery path on this system) and the
fullscreen element API (no UIKit implementation here). WebAssembly needed no
decision - `PlatformEnable.h` already forces it off on `CPU(ARM)`.

**Stripping costs symbolization.** A death log afterwards named a frame
"`WindowProxy::window() + 478666`", which is the nearest exported symbol plus
nonsense. Unstripped copies now live in `dist/unstripped/`, and the profiler's
`image <base> <path>` lines give the slide, so
`atos -o dist/unstripped/WebCore -arch armv7 -l <base> <addr>` reads them
properly. That is how the next crash was actually diagnosed.

## Content filtering: the crash that had nothing to do with size

The `-Oz` build died on its first navigation, SIGSEGV. Symbolized against the
unstripped copy:

    ThreadSafeRefCounted<PlatformContentFilter>::ref()
    WTF::ThreadSafeWeakPtrControlBlock::strongRef()
    WebCore::ContentFilter::continueAfterWillSendRequest(...)
    WebCore::DocumentLoader::willSendRequest(...)

`ContentFilter::create` builds its container with
`types().map([](auto& type) { return type.create(params); })` and only checks
whether the container is *empty*. On this system there is no content filtering
service at all - no `WebFilterEvaluator`, no `NEFilterSource` - so each type's
`create` hands back nothing, the container holds empty references, and the first
request dereferences one. `ContentFilter::create` now returns null on this port,
which callers already handle; this is not the same as disabling the feature at
build time, which was tried earlier in the project and broke the build.

## Where memory went next, and the shape of the remaining trade

With the engine 25 MB smaller, resident did not fall: the JavaScript heap grew
into the space, to **45.5 MB with a 53.8 MB capacity**, because JSC sizes its heap
from the RAM hint we pass it. Halving `JSC_forceRAMSize` from 128 MB to 64 MB
brought the heap to 29.4 MB / 44.3 MB capacity and resident from 159 to 151.8 MB,
with the worst frame rate still 55 and no new stalls. This is the honest trade to
keep measuring: a tighter heap is less memory and more collection.

Both login crashes were memory, not the keyboard: first SIGTRAP inside `malloc`
under `Exception::finishCreation` (capturing a hundred frames of stack for a
thrown exception - now capped at 25), then `abort` through `std::terminate`, an
uncaught `bad_alloc`, at 165 MB resident with a 171.5 MB peak.

## The freeze, taken apart

A sampler that records the web thread **only while the engine is inside a call
from C++ into script** - a counter JSC raises across `profiledCall`, read by the
sampler through `dlsym` - gave 687 samples inside passes of 11.8 and 8.2 seconds.
Categorised by the innermost frame, which is the only frame that says where time
goes:

| | share |
|---|---|
| JS: property lookup (`operationGetByIdGaveUp`, `PropertyTable::find`) | 17.6% |
| unsymbolized (JIT-compiled code) | 14.7% |
| JS: compile and parse | 10.2% |
| malloc / mmap | 7.6% |
| layout | 4.7% |
| JS: call machinery | 2.8% |
| locks / waiting | 2.6% |
| JS: interpreter body | 2.3% |
| style recalc, GC, paint, fonts | under 1% each |

A first pass at this categorisation said "48.6% interpreter" and was wrong: it
matched patterns against the whole stack, and interpreter dispatch frames appear
in almost every JavaScript stack as callers. Same error class as the bar
measurement - measuring something adjacent to the question.

So the freeze is JavaScript, rendering is under six percent of it, and three
candidate fixes were tested and eliminated rather than assumed:

- **Megamorphic property access is not the problem.** A benchmark of forty
  differently-shaped objects read in a hot loop: 69 ms megamorphic against 59 ms
  monomorphic, a ratio of 1.2. Raising `maxAccessVariantListSize` from 8 would
  buy nothing. The cost is the *number* of accesses, not the price of one.
- **Code is not being thrown away.** `useUnlinkedCodeBlockJettisoning` already
  defaults to false and `useCodeCache` to true, so the 10.2% of compilation is
  first-time lazy compilation of a large bundle, not re-parsing.
- **Compiling sooner is worse.** `thresholdForJITAfterWarmUp` 500 → 100 and
  friends: passes of 5.4, 12.6, 10.3, 1.7, 0.7 s and 174 MB resident, against
  3.9, 9.7, 10.3, 1.0 s and 151 MB at upstream values. Reverted.

That A/B cost no rebuild: `app/native-main.m` now reads `/tmp/native-jsc-options`
as `KEY=VALUE` lines and sets them before the re-exec, so any JSC option can be
compared on the device in minutes.

## The last lock, and what it was costing

Both of `WebViewRenderingUpdateScheduler`'s run loop observers open their bodies
with `WebThreadLock()`. A run loop observer binds to whatever run loop schedules
it, once, and never rebinds - so one scheduled from the main thread becomes a
main-thread web-lock acquisition on every turn of the main run loop. Under
`WEBKIT_IOS6`, `scheduleRenderingUpdate()` now hops to the web thread first when
called from anywhere else, where the same lock is a recursive no-op.

That was the last main-thread lock take of this kind, and it was not costing 89 ms
as the census suggested - it was starving the web thread. With it gone, and with
every instrument of mine switched off, three verified runs in a row (kill, confirm
dead, clear logs, launch, confirm started, wait):

| alive at end | yes | yes | yes |

## Both cores are working

Worth recording because I got this wrong in a report: the A5 is dual core at
800 MHz, not single core. Per-thread CPU during a load: the web thread at 57, 98,
64 and 89 percent, and a second thread at 39 to 57 percent at the same time. The
second core is not idle - JavaScriptCore gets one DFG compiler thread
(`computeNumberOfWorkerThreads(3, 2) - 1` with two cores), GC marking is parallel,
and `LargeImageAsyncDecodingEnabled` is on for WebKitLegacy.

What is single-threaded is the *page*: WebCore does style, layout and script on
the web thread under one lock, and WebKit has no parallel layout. So the second
core helps compilation and collection, and cannot help a render.

## Stripping is now part of packaging

A deploy that used `strip -S` without `-x` put the engine back to 98.8 MB from
65.8 - thirty three megabytes on a device that is killed at about a hundred and
seventy. `build-app-lto.sh` now strips the three frameworks itself and keeps
unstripped copies in `dist/unstripped/` for symbolising crash logs, so it cannot
be skipped by hand again.

## The injected script was never in the page for whole sessions

`installBridge` and `applyInjection` hung off `webViewDidFinishLoad:`, and this
site never reaches it - it keeps connections open and the delegate callback does
not arrive. Measured on the device: `window.__appchromeV` read **0** and
`window.appchrome` was **undefined** after a full load. So everything that depends
on the injection had been silently doing nothing: the install sheet was never
dismissed, nothing was retargeted, no bars could be promoted. The earlier fix -
shipping `inject.js` at all - only got the file onto the device; it still was not
being evaluated.

It is now keyed to the scroll view's content size passing one screen, which is
the cheapest evidence that a document exists and takes no locks, once per
document rather than on a poll, with the flag cleared when a main-frame
navigation starts. `window.__appchromeV` now reads 15 and the bridge is present.

And the evaluation itself moved off the main thread. Two
`stringByEvaluatingJavaScriptFromString:` calls with a nine kilobyte script were
the only dip in the frame rate for a whole session - to 25 fps, with two stalls.
It now goes through the engine's own window object from inside `WebThreadRun`.

## Promoting the site's bars to real controls

Implemented as the design in `notes/shared-engine-architecture.md` describes:
the page finds its own fixed bottom bar, reports its items through the bridge
(`window.appchrome.chrome`, a new `describeChrome:` selector), and hides it; the
application draws real views outside the web view and turns taps into
navigations. A pinned bar drawn this way cannot drift - it is not inside the
layer UIKit slides, so there is no per-frame counter-movement to get wrong, and
the engine carries one composited layer fewer.

It works - "native bottom bar with 2 items" - and it is **deliberately not
engaging on this site**. Threads draws five items in that bar and only two of
them are `<a href>`; the rest are `role=button` with no navigable target. A native
bar with two icons where the site shows five is worse than the one it replaces,
so the promotion now requires every visible item to be reproducible and otherwise
leaves the page's own bar alone, which is the fallback the design asks for.
Finishing it for this site means mapping the three button items to something the
page will act on - the bridge's deferred press already exists for exactly that.

## An optimisation attempted twice and rejected twice

Symbolising a load stall properly - against `dist/unstripped/WebCore` with the
image base the app now logs at launch - named it exactly:

    RenderBox::computeContentAndScrollbarLogicalHeightUsing
    RenderBox::computeLogicalHeightUsingGeneric
    RenderBox::constrainLogicalHeightByMinMax
    RenderBox::computeLogicalHeight
    RenderBox::updateLogicalHeight
    RenderBlockFlow::layoutBlock
    RenderBlock::layout
    RenderBlockFlow::layoutBlockChild
    RenderBlockFlow::layoutBlockChildren

A full recursive layout of the feed, on the **main** thread, over 400 ms. It comes
from `-[WebHTMLView viewWillDraw]`, which calls
`_web_updateLayoutAndStyleIfNeededRecursive` whenever the view is about to draw -
and on this port CoreAnimation asks the tile layers to draw during the main
thread's commit.

Skipping it when the main thread is the one drawing:

| | load, worst fps | scroll |
|---|---|---|
| skip on the main thread | 47 - 54 | **10 - 14** |
| lay out as upstream does | 13 - 15 | **56 - 60** |

The tile then draws from a stale layout, the engine invalidates it, and the frame
is spent twice. Skipping it only while the application reports no scroll in
progress - a flag the app raises as it publishes each offset, read by the engine
through `dlsym` - failed the same way: during a flick the flag is clear between
frames, the layout is skipped anyway, and scrolling fell to 8 fps.

Reverted, with the measurement written into the comment so it is not attempted a
third time. The load stall is the cheaper of the two, and scrolling is what a
person feels.

Also fixed while here: stack frames now print the raw address alongside the name.
On a stripped binary `dladdr` answers with the nearest exported symbol plus a
large offset, which reads as a confident wrong answer - two stalls were "diagnosed"
from such nonsense before I noticed. The app logs each framework's load address
once at launch, so any frame can be resolved offline:
`atos -o dist/unstripped/WebCore -arch armv7 -l <base> <address>`. Note the base
changes per launch - using a previous run's base produces plausible, wrong symbols.

Final state of this stretch: scroll **60.0 / 60.0 / 60.0**, no stalls during
scroll, load dip to 13, resident 157 MB, engine 65.8 MB, alive.

## What the load actually spends its time on

The page's own Navigation Timing, read from the device:

| | |
|---|---|
| DNS, connect, request, first byte | all at **13 ms** - the document came from cache |
| transferred, 85 resources | **6 KB** - the scripts and styles were cached too |
| domInteractive | **8737 ms** |
| domContentLoaded | 8900 ms |
| loadEventEnd | 19482 ms |

So with the document and every script already on the device, it still takes
**8.7 seconds** to reach an interactive DOM. That is parsing and script execution
on this processor, nothing else - no network to blame. And the further ten
seconds to `loadEventEnd` are images.

Per host, from Resource Timing:

| host | requests | min | median | max |
|---|---|---|---|---|
| instagram.flcj1-1.fna.fbcdn.net | 14-23 | 145 | 1633-2958 | 11958-17111 |
| scontent.cdninstagram.com | 8-15 | 86 | 1108-1977 | 2035-6724 |

| static.cdninstagram.com | 33 | 66-105 | 470-487 | 2378-3195 |

## The per-host connection limit is a memory lever, not just a speed one

It is now readable from the environment (`WEBKIT_IOS6_MAX_CONNECTIONS`, default 6)
so it can be swept on the device instead of rebuilt. Measured, one clean verified
run each:

| connections | worst frame rate | stalls | resident / peak |
|---|---|---|---|
| 4 | 33.4 | 1 | 154.8 / 157.3 MB |
| **6** | **53.5** | **0** | 158.1 / 163.6 MB |
| 14 | 54.0 | 0 | **298.9 / 302.0 MB** |

Fourteen parallel image fetches nearly doubled the process. Six is better than
four on both frame rate and stalls for three megabytes, and going up is not
survivable on a device that is killed in this range. Six stays - now verified
across {3, 4, 6, 14} rather than assumed from a single earlier comparison against
"unlimited".

So the remaining load cost is not the network. It is 8.7 seconds of parsing and
executing a cached bundle, which is the same wall the freezes ran into: the volume
of the site's JavaScript against this processor.

## What the 8.7 seconds before an interactive DOM are made of

The sampler had to be made honest first: it now records **raw addresses only**,
with no `dladdr` in the loop. That call walks a symbol table on every frame of
every sample, and with it in there the sampler doubled the pauses it was
measuring - eleven seconds where five was the truth. Addresses resolve offline
against `dist/unstripped` using the image bases the application logs at launch,
and it can now sample the whole window rather than only inside script
(`/tmp/native-profile-scoped` picks between the two). With it running: worst frame
rate 55.5, zero stalls - it no longer perturbs what it watches.

3507 samples of a load window, categorised by the innermost frame inside our own
images:

| | samples |
|---|---|
| `RunWebThread` - the web thread parked in its own run loop | **825 (24%)** |
| `WTF::fastMalloc` | 76 |
| interpreter dispatch | 79 |
| `operationGetByIdGaveUp` | 53 |
| `tryFastCompactAlignedMalloc`, `fastZeroedMalloc` | 37 |
| lock acquisition | 24 |
| `FontDatabase::collectionForFamily` | 18 |
| everything else | a long tail of 5-9 each |

Two things follow. **A quarter of the load is the web thread idle**, so the load is
not continuously CPU-bound - it waits. And there is **no hot spot**: after the idle
samples the largest single leaf is two percent. The 8.7 seconds is not one fixable
thing, which is worth knowing before spending another day looking for one.

## One real find in the tail: the font family list was rebuilt on every call

`CTFontManagerCopyAvailableFontFamilyNames` in `compat/ios6_coretext.c` created the
whole font collection, matched every descriptor and deduplicated the family names -
per call. Real CoreText answers that from a cache, and the engine asks whenever it
resolves a family it has not seen, which is why it surfaced under
`FontDatabase::collectionForFamily`. Now built once behind a mutex; the installed
fonts do not change while the process runs.

Measured, clean flags, verified runs:

| | before | after |
|---|---|---|
| resident | 157 - 158 MB | **146 MB** (peak 147 - 152) |
| scroll | 60 / 60 / 60 | 60 / 57 / 60, zero stalls |

Eleven megabytes of headroom on a device that is killed in this range, for a
cache that cannot go stale.

A caution recorded from the same session: a run measuring 239 MB resident turned
out to have `/tmp/native-engine-log` still set, which makes the tile code write to
an unbuffered stderr from the web thread. Every measurement here needs the flags
cleared first, which is what `/tmp/measure.sh` does - the one run I took without
it was wrong by ninety megabytes.

## Two seconds of the web thread standing still, per load

The load profile said the web thread is parked a quarter of the time. Part of
that is a mechanism worth naming: every synchronous delegate message from the
engine wakes the main thread and then **blocks** the web thread until it answers -
`SendDelegateMessage` signals a run loop source and waits on a condition. Counting
it over one load (a clock read per message, behind `/tmp/native-delegate-cost`):

    419 messages, 1939 ms blocked in total, slowest 1216 ms

And per selector, which is where it got interesting:

| | total | count |
|---|---|---|
| `postNotificationName:object:userInfo:` (`WAKViewFrameSizeDidChangeNotification`) | 1450 ms | **2** |
| `webView:identifierForInitialRequest:fromDataSource:` | 1310 ms | **1** |
| `webView:decidePolicyForNavigationAction:...` | 112 ms | 1 |

**The frame-size notification was already queued asynchronously** - the code that
posts it says so, with an rdar number, precisely to avoid relinquishing the web
lock mid-layout. But the queue is drained in `WebRunLoopUnlockInternal` by calling
`SendDelegateMessage` on each entry, which blocks. So "async" deferred the block
without removing it. Dispatching each queued invocation to the main run loop
instead keeps the lock on the web thread and lets it carry on; the ordering given
up is between no-reply messages and later synchronous ones, which queueing them
asynchronously had already conceded.

**The 1310 ms in a single `identifierForInitialRequest`** is not the delegate being
slow - it is the first delegate message of the load arriving while the main thread
is still building the window, so the web thread waits for it to reach its run
loop. The application now starts the load one turn later, from
`performSelector:withObject:afterDelay:0` rather than inside
`didFinishLaunchingWithOptions:`.

Measured, A/B'd behind `/tmp/native-block-async-delegates` with clean logs each
run:

| | delegate blocking | slowest message | resident | load worst fps |
|---|---|---|---|---|
| blocking, as upstream | 1283 ms | 621 ms | 171.1 / peak 176 | 42.1 |
| **dispatched** | **411 ms** | **108 ms** | **163.5** | **50.1** |

With the deferred first load on top, the original 1939 ms becomes 368-467 ms - a
little over two seconds of web-thread standing per load recovered. Scrolling over
sixteen flicks afterwards: **60.0, 58.5, 60.0, 60.0**, no stalls, resident 158 MB.
One 12.2 fps window seen in an earlier run belonged to the load, not to this
change - it does not recur once the page has settled.

A process note that cost two confusing measurements: `/tmp/native-stderr.log` was
not being cleared between runs, so the engine's cumulative counters read as if
nothing had changed. `/tmp/measure.sh` now clears it along with the rest.
